## How versions work

A version is a git tag `vX.Y.Z`. The driver reports `git describe`: `v0.13.2-59-g2f04e1e` means 59 commits after `v0.13.2`.

To make a release:

1. Move the items under Unreleased to a new heading `## [vX.Y.Z] — date`.
2. Add the section and the compatibility row to `UPGRADE-GUIDE.md`.
3. Set `version` and `appVersion` in `charts/ibm-vpc-file-pool-csi/Chart.yaml` to `X.Y.Z`.
4. Tag the merge commit `vX.Y.Z` and push the tag.

`v0.11.0`, `v0.13.0` and `v0.13.1` were tagged on 21 October 2026, at the commit that added their changelog entry. `v0.13.2` sits at `e2b780f`, the last commit of 25 February 2026: the commit that first added its entry (`a2c2a07`) lacked the TLS work the entry names. `v0.10.0` and `v0.12.0` were written in the same commits as `v0.11.0` and `v0.13.0`, so they have no tag of their own. The chart said `0.1.0` until `v0.14.0`.

## [v0.14.0] — 2026-10-22

This release adds backup to a snapshot pool and to IBM Cloud Object Storage (COS), instant VM snapshots, replication of running VMs, 21 alerts with real share usage and latency, image and controller hardening, and many fixes.

**File-level restore from a backup (issue #92) is NOT in this release.** Only its first two parts are here (the browse helper image and the `BackupBrowse` resource); the console and `kubectl backup` do not offer a file restore yet.

### Added (latest changes)

- **Replication and backup status follow the copy Jobs within seconds (issue #192).** Before, a policy looked at its Jobs only when its schedule was next due, so `sync in progress` stayed for the whole schedule (a first backup took about 13 minutes to show LAST BACKUP). Now a policy with a cycle in progress is checked on every poll (30 seconds), the controllers also watch the Jobs in the driver namespace and wake when one finishes, and the backup controller wakes after each replication pass. Pre-sync hooks still run once at the start of a cycle, and the cycle's duration is measured from its start.

- **Release test stage 16: browser tests for draining a share, migrating a claim and cloning a volume (issue #46, items 5 to 7).** Each drives the console page with a token that has only the rights of that page, then checks the cluster. Found issue #196 (migrate fails for a user without the root right on OpenShift).
- **Browse helper for single-file restore, part 1 (issue #92).** A new image (`browse`, built by `make docker-build-browse`) and program (`cmd/browse`) that read one backup folder read-only: list, stat, read a byte range, or stream a tar, over HTTP with a session token. Links are listed and never followed, names are raw bytes, and a pipe or device is never opened. It ends when idle or at a time limit. Nothing in the driver starts it yet, so users see no change. Lab result: with root, no capabilities and a read-only mount, it reads another user's files with mode 0600 and folders with mode 0700, so the restore Job that copies as root can too. Release test stage 20 (the spec calls it 19; 19 is taken) checks this on a real share.
- **Instant VM snapshot of a disk owned by another user (issue #191).** Before, it failed after the snapshot was taken with `chmod: changing permissions ... Operation not permitted` and left an extra overlay file in the disk chain. Now the driver checks the owner of `disk.img` first and refuses before changing anything, with a message that names the owner and the fix. The Snapshot is marked Failed with that message. If a step fails after the new overlay file is made, the driver merges the file back and deletes it, so the chain is as it was.
- **Browse sessions for single-file restore, part 2 (issue #92).** New cluster-scoped `BackupBrowse` resource and the backup controller part: a helper pod per open session, with a per-session token and TLS certificate in a Secret, limits (15 minutes idle, 2 hours hard, 5 sessions in the cluster and 2 for each namespace), and clean-up of helpers and Secrets whose session is gone. The helper now serves only over TLS and can read a chosen moment. New chart values `backupBrowse.*`, a Role for the session Secrets in the release namespace, and a NetworkPolicy. Users cannot start a session yet: the gateway comes in part 3. Every object of a session is named by the resource's UID, so a deleted session that is made again with the same name cannot get the old session's Secret or pod.

- **Browse helper for single-file restore, part 1 (issue #92).** A new image (`browse`, built by `make docker-build-browse`) and program (`cmd/browse`) that read one backup folder read-only: list, stat, read a byte range, or stream a tar, over HTTP with a session token. Links are listed and never followed, names are raw bytes, and a pipe or device is never opened. It ends when idle or at a time limit. Nothing in the driver starts it yet, so users see no change. Lab result: with root, no capabilities and a read-only mount, it reads another user's files with mode 0600 and folders with mode 0700, so the restore Job that copies as root can too. Release test stage 20 (the spec calls it 19; 19 is taken) checks this on a real share.
- **Console: the restore page no longer spins forever without the right to read VolumeSnapshotContents (issue #186).** It now says which right is missing.

- **Console: the delete backups dialog gives an administrator the safe command.** When the user lacks the rights, the dialog now shows `kubectl backup delete --policy <policy> --pvc <namespace>/<name>`, which measures first and asks for the typed claim name. Before, it showed raw YAML that removed the backups with neither step.
- **The documents moved into `docs/` (issue #116, part 1).** README, CHANGELOG, CONTRIBUTING, CLAUDE.md and SKILL.md stay in the root; every other guide is now in `docs/`, and the research notes are in `docs/archive/`. All links, the console's help links, the docs site and the code comments point to the new places. A branch that still edits a guide at its old place: after `git merge origin/main` stops, run `hack/follow-docs-move.sh` to carry the edits over.

- **Receiver check on the policy: `ReceiverReachable` (issue #46, item 4).** For a policy in driver-to-driver mode, the replication controller now checks the receiver (it answers, the certificate is trusted, the token is accepted) when it first sees the policy and then once per schedule, and sets the `ReceiverReachable` condition on `status.conditions` with a plain reason such as "certificate not trusted" or "token refused". The Replication Policies list has a Receiver column with help text, and the policy page a Receiver Status line. A failing check does not stop replication. The controller reads the two Secrets in `kube-system` with the rights it already has.
- **Console: the VM warnings on the restore and clone pages are correct again.** The restore page no longer says a snapshot of a running VM may not boot; it says the disk was copied at one moment, and what a crash consistent copy means. The clone page points to a VM snapshot for a safe copy.

- **Console says when Red Hat does not support a VM copy.** The replication policy pages (when the policy holds a running VM's disk) and the Snapshots page now say that copies and snapshots of running VMs work directly with QEMU, not through OpenShift, so an OpenShift update could stop them until the driver is updated. The Snapshots page adds that instant snapshots also need a KubeVirt setting Red Hat does not support.

- **Sidecar gate Job has fewer rights (issue #154).** The hook Job that `vmSnapshots.enableSidecarGate` runs may now only get and update the `HyperConverged` object named `kubevirt-hyperconverged` in `openshift-cnv`; before, it could list and update every `HyperConverged`. SECURITY.md now says what the gate opens up.

### Security
- **Image hardening (issue #90).** The driver image now runs as user 65532 (`USER` in the Dockerfile). The chart sets security contexts: the controller is non-root with no privilege escalation, all capabilities dropped and the `RuntimeDefault` seccomp profile; its sidecars get no escalation and no capabilities; the console plugin and replication receiver get the same limits. The node agent explicitly stays root and privileged (it mounts NFS), and Jobs the controller creates keep the users they already set. All of it can be overridden with `controller.securityContext`, `controller.podSecurityContext`, `controller.sidecarSecurityContext`, `node.securityContext`, `replicationReceiver.securityContext` and `consolePlugin.securityContext`. **Not lab tested.** Off OpenShift the chart adds `fsGroup: 65532` to the controller so it can read the webhook key.

### Changed
- **The default image tag is `v` plus the chart `appVersion`, not `latest` (issue #90).** `image.tag` and `consolePlugin.image.tag` are empty by default. `make deploy`-style installs that set `--set image.tag=...` are unchanged. The chart `appVersion` must be set at release (it is `0.1.0` until then), so an install without `image.tag` before a release asks for an image that does not exist.

### Fixed
- **A VM disk copy no longer sticks for good when its finished apply Job expires before the controller reads it (issue #160).** The apply step now treats a missing staging file as done when the far-site disk already shows that copy, so the Job the controller makes again succeeds. The volume shows "apply Job was gone before its result was read; running it again" meanwhile. Deleting a replication policy now also removes its temporary Jobs, PVCs and PVs in `kube-system`. Tested with fakes and temporary folders; not lab tested.
- `kubectl backup delete`, found by the lab test of issue #124: a shell whose input is `/dev/null` (a script, CI) counted as interactive, so the command measured the backup and then asked a question nobody could answer, instead of stopping at once as documented; and the size it showed counted every hard-linked file twice for plain volumes. The size is now one `du` run over both folders. `BACKUP-RECOVERY.md` lists every right the command needs.
- **Dashboard numbers that did not match their labels.** The Allocation Rate cards (dashboard and pool page) showed new volumes per second under a "/hr" label; they now show per hour. The Snapshots card counted every snapshot operation, including deletes and failures; it now counts snapshots taken. The Clones card counted failed clones too, and labelled the median clone time "Avg duration"; it now counts finished clones and says "Median duration".
- **`kubectl backup cos-setup` could never finish a first run, and lost the HMAC secret (issue #138).** IBM Cloud adds an instance-wide Writer policy to the service ID when the HMAC key is made; the safety check then stopped the command before the key file was written. Now the key file is written the moment the key is made, the command deletes that one implicit policy (found by comparing the service ID's policies before and after; it says so in the steps) and then runs the check, which still refuses any other wide policy. A rerun with an HMAC key that exists makes no second key and says its secret cannot be shown again (delete the key to get a new one). A key file with no HMAC key stops the command before a key is made. Found in the first live run; tested with fakes, not rerun on IBM Cloud.

- **COS export, part 5: restore from COS and `kubectl backup cos-list` (not tested against a real bucket or Key Protect).** `kubectl backup restore --from-cos` makes a new PVC from a backup in a COS bucket, in any cluster that runs the driver: no `BackupPolicy` and no snapshot pool are needed. A `BackupRestore` has a new optional block `spec.fromCOS` (bucket, endpoint, prefix, credentials Secret, `volume`, `sizeGB`, wrapped-key Secret and `keyProtect`, or `emergencyKeyOnly` with `emergencyKeySecret`); `sourceNamespace` and `sourceName` are required only without it. Three Jobs run on the new volume's share: one restores the export read-only from the Kopia repository into a scratch folder, the restore Job of a local restore copies it into the volume, and one removes the scratch folder. Status has two new fields, `fetched` and `copied`. The command removes delete markers in the policy's area with the caller's own IBM Cloud login (markers only, by version), makes the wrapped-key Secret from the bucket if the cluster has none, and with `--backup-key-file` restores with the readable key and never calls Key Protect (its temporary Secret is removed when the restore ends). `kubectl backup cos-list` lists the volumes and the export moments in the bucket with a read-only Job. - **COS export, part 3: key handling (not tested against a real Key Protect instance).** The backup key is stored only as a Key Protect-wrapped copy. `spec.export` has a required `keyProtect` block (`instanceID`, `region`, `rootKeyID`, `apiKeySecret`) and an optional `emergencyKeySecret`; `backupKeySecret` now holds `wrappedKey`, not a readable key (the Secret `cos-setup` writes). Export and maintenance Jobs no longer have `KOPIA_PASSWORD`: they mount the wrapped key, the API key and the optional emergency key as read-only Secret files and run the driver in a new mode, `unwrap-backup-key`, which unwraps the key with Key Protect and writes it (mode 0400) to a memory-backed folder; the script hands it to Kopia and deletes the file. If Key Protect is unreachable (no connection, a 5xx or 429) and an emergency key is set, the Job uses it and logs that it did; a refusal from Key Protect (wrong root key, bad API key) never falls back. The controller never reads these Secrets and never calls Key Protect (tests check both). New package `pkg/keyprotect` (plain `net/http`, no new dependency; IAM token from the API key, `wrap`, `unwrap`). The webhook refuses a block without the four `keyProtect` fields. `cos-setup` now prints the `keyProtect` block and the command for the API key Secret. Tested with a fake Key Protect HTTP server and a Kopia repository in a folder.
- **COS export, part 4: `kubectl backup cos-setup` (not run against real IBM Cloud yet).** Automates `TUTORIAL-09-COS-BACKUP-BUCKET.md` with the caller's own IBM Cloud login (an IAM token or API key from the environment, or the `ibmcloud` login; never stored or printed): the COS instance, a bucket with versioning and object lock encrypted by a Key Protect root key you give, the custom role `PoolCsiBackupWriter` (the action list is in one place, `pkg/cossetup/roles.go`, and a test checks it against the tutorial and that it leaves out `object.delete_version`, `object.bypass_governance_retention` and every `bucket.put_*` and `bucket.delete_*`), a service ID and HMAC key limited to the one bucket, a CBR zone and rule, and a backup key wrapped by Key Protect. It reuses what exists by name, never deletes anything, refuses a bucket it did not make unless `--existing-bucket`, refuses an enforced CBR rule when the caller's own address is not in the zone, supports `--dry-run`, asks for a typed confirmation (or `--yes`), and for a keep time above 90 days asks for a second one. It writes the COS key to `--key-file` (Secret manifest, mode 0600), shows the readable backup key once and waits for a typed confirmation that a copy is saved, then stores only the wrapped copy in the bucket and in `--secret-file`. It prints the `spec.export` block. New package `pkg/cossetup` (plain `net/http`, no new Go dependency); tested with httptest fakes of every API. The Key Protect wrap is a small client inside `pkg/cossetup`, to be joined with `pkg/keyprotect` later.
- **COS export, part 2: the controller, status, metrics and the webhook (needs key handling, part 3, to be usable).** A `BackupPolicy` has an optional `spec.export` block (bucket, endpoint, prefix, `credentialsSecret`, `backupKeySecret`, `keepFor` default 30d, `lock` Compliance or None, optional `schedule`). After a local backup of a volume finishes with a moment newer than the last export, the controller starts an export Job for it (one at a time for each policy) and puts the result in the volume's status: new fields `exportedTime`, `exportedBytes` and `exportError`. A failed export is retried after 5 minutes. An export problem never changes the policy's phase or stops the backups to the snapshot pool. Once a volume is exported, a maintenance Job runs every maintenance interval (a day; an hour for the shortest keep time) to extend locks and now also to delete Kopia snapshots older than `keepFor`; the export sets a Kopia policy so that Kopia itself never drops snapshots by count. The webhook refuses an export block without bucket, endpoint or Secrets, a lock other than Compliance or None, and a Compliance `keepFor` below 25 hours; the rule is one helper used by the webhook and the controller. `ExportToCOS` and `MaintainCOSRepo` are now in the `ShareData` interface. New metrics `vpc_file_pool_backup_export_oldest_unexported_age_seconds` and `vpc_file_pool_backup_export_newest_age_seconds` with example alerts (`ExportLate`) in `MONITORING.md`; the chart alerts are issue #117. Tested with fakes and with a Kopia repository in a folder; not tested against a bucket or on a cluster.
- **COS export, part 1: Kopia in the image and the export Jobs (not used by the controller yet).** The driver image now holds the Kopia program (0.23.1, checked by SHA-256 in the `Dockerfile`; used only by Jobs, not linked into the driver). `ShareJobRunner` has two new methods, `ExportToCOS` and `MaintainCOSRepo`, that are not in the `ShareData` interface. The export Job mounts the snapshot share read-only, connects to (or creates) the Kopia repository in the bucket, and snapshots a volume's backup folder and its moments folder, tagged with the moment and the volume; the termination message carries the moment and the bytes sent. The maintenance Job runs `kopia maintenance run --full`, and with a Compliance lock first turns on lock extension. Keys come from Secrets, never in the script or its arguments (part 3 replaced the backup key's environment variable with the Key Protect unwrap). A Compliance keep time shorter than the maintenance interval plus 24 hours is refused. Tested against a Kopia repository in a folder; the MinIO test runs only when `MINIO_ENDPOINT` is set. Spec: `docs/specs/2026-10-21-backup-cos-export.md`.
- **A snapshot pool can have more than one share (issue #71).** A new volume is backed up to the ready share that has room and holds the fewest volumes; its backups stay on that share for good, and a restore reads from it (`shareID` in the volume's status; an entry made before this change belongs to the first share). A policy makes one replication policy for each source pool and share. The 85% limit works for each share: only the copies to a full share stop, and new volumes avoid it. A new volume that no share can take waits and says so. The metric `vpc_file_pool_backup_snapshot_pool_used_percent` has a new label `share`. `kubectl backup delete` reads the share from the status; for a deleted policy, `--share` names it when the pool has more than one.
- **Backups stop when the snapshot pool is more than 85% full (issue #69).** A small Job on the snapshot share reads its usage (`df`) about every 10 minutes. Above 85%, the `BackupPolicy` goes to `Error` with the usage in `status.message`, and its owned `ReplicationPolicy` objects get the paused annotation (as `suspend` does). Backups are never deleted to make room, and resume when usage falls to 85% or less. New metric `vpc_file_pool_backup_snapshot_pool_used_percent`; alert rules in `MONITORING.md`.
- `kubectl backup delete --policy P --pvc NS/NAME [--yes]` removes the backup folder and the earlier moments of one volume from the snapshot pool, with a Job on the pool's share. It shows the paths and the size and asks for a typed confirmation first; `--yes` is required in a shell that is not interactive. It refuses while the policy still backs up the volume or a restore of it runs. The controller never runs it. A deleted policy needs `--pool` and `--volume` (issue #70).
- **Instant VM disk snapshots (Experimental).** Where the KubeVirt `Sidecar` feature gate is on, a snapshot of a VM disk is a new overlay file, as in VMware: nothing is copied, and the snapshot is ready in seconds whatever the disk size. It is taken inside `CreateSnapshot`, so an OpenShift VM snapshot gives every disk of a VM at the moment OpenShift froze the guest; before, each disk was copied later, one after another (issue #14). Deleting a snapshot merges its file while the VM runs. Restoring is one sparse `qemu-img convert`. A mutating webhook gives a VM with snapshots the driver's hook when it starts; frozen files are read-only, so a VM that starts without the hook fails safe. New: Helm `vmSnapshots.method` and `vmSnapshots.launcherImage`, flags `--vm-snapshot-method` and `--virt-launcher-image`, SubVolume `status.diskChain` and `status.chainOperation`, Snapshot `status.chainFile`, `status.mergeChild` and `status.methodReason`, and the `kubectl pool-snapshots flatten` plugin (`make build-pool-snapshots`). Design and lab results: [VM-INSTANT-SNAPSHOTS.md](docs/VM-INSTANT-SNAPSHOTS.md).

- **Group snapshots are no longer shown as a working feature (#100).** Nothing acts on a `VolumeGroupSnapshot` and the hooks never ran, so the docs now say "not active" and the console no longer has the Group Snapshots tab or its pages. The code and the record type stay.
- **Docs no longer say the VPC API has no share snapshot operation.** It has one. The driver does not use it, because a share holds many volumes (#101).
- **The console dashboard no longer shows "NaN ms" and a red "High" when there were no allocations.** No data now shows "-" with no label (#113).
- **Console plugin libraries updated: advisories down from over 60 to 14.** The 14 left are build tools or have no fix; each is listed with its reason in `osv-scanner.toml` and expires on 2026-12-31. Go libraries `mongo-driver` and `x/crypto` updated too. New CI job "Dependency scan" fails on any other known advisory (#90).
- `kubectl backup` and `kubectl failover` now use the `KUBECONFIG` variable when `--kubeconfig` is not given, as kubectl does. Before, they read only `~/.kube/config`.
- **A backup policy with a longer name could not copy plain volumes.** The name of the replication policy a backup policy makes (`backup-<policy>-<pool>-<hash>`) is a label value on the temporary volume of a copy, and it went over 63 characters for a policy and pool name of about 25 characters each. The copy failed on every cycle with "must be no more than 63 characters", and the VM disks, which use another path, still worked. The name is now cut to fit; names that already fit stay as they were. Found by release stage 18 on the lab.
- **A VM disk made by a CDI clone (for example a VM from the OpenShift console catalog) is now seen as the VM's disk.** CDI provisions the clone through a temporary claim and then binds the volume to the VM's claim; the SubVolume kept the temporary claim. The driver then did not find the running VM, so a snapshot of a running VM's disk was a plain file copy, not an instant or QEMU snapshot. A new controller sets the SubVolume's claim to the claim its volume is bound to, also for volumes that exist already.
- A slow snapshot, snapshot delete or restore no longer makes every other volume's create and delete wait. Each of these calls now locks only the volume it changes; the driver-wide lock is held just for the share's space bookkeeping. Two changes to the same disk still never run at once (issue #99).
- Deleting a pool no longer deletes the data of its snapshots. The pool waits while snapshots exist (`DeletionBlocked` reason `SnapshotsExist`), and a drained share counts its snapshots too (new `status.drainStatus[].remainingSnapshots`). A snapshot whose pool an older driver already deleted can now be deleted; before, its delete was stuck for ever (issue #96).
- A snapshot's space charge on its share now survives the pool's regular recount; before, the next reconcile dropped it, and the later delete then counted the share too low. A snapshot no longer counts as a PVC, and a share that has no room for a snapshot refuses it with `ResourceExhausted` instead of being over-committed (issue #97).
- A restore into a volume smaller than the snapshot is refused (`OutOfRange`) instead of making a volume the data does not fit in (issue #98).
- Replication finds a VM disk whose top file is not `disk.img`.

### Changed
- **VMs now come from the standard OpenShift Virtualization catalog.** Pick a catalog image and choose the pool's StorageClass for the boot disk. CDI copies the image onto the pool. The controller keeps the memory limit of CDI's copy pods at least 8Gi, through `HyperConverged` `spec.resourceRequirements.storageWorkloads`. CDI's default of 600 MB is too small for copies onto NFS: the pod is killed. Measured on rovslab on 20 October 2026: a 25 GB copy with a 2Gi limit was killed 6 times and never finished. With 8Gi it finished in 134 s and the checksum matched. A RHEL 9 catalog VM on a pool had its guest agent after 103 s.
- **Golden images are hidden from the console pool form.** The pool form no longer offers them, and the "VM storage" preset no longer turns them on. The code is kept for possible later use, and `spec.goldenImages` still works if a pool sets it in YAML. The standard catalog is the recommended way.
- The release test makes its VMs from the standard catalog (stage 08), copies 25 GB from Ceph with CDI and checks the checksum, and checks CDI's copy pod limit in stage 01.
- Release test stage 16 restores a snapshot to a new claim in a real browser (issue #45, part 2). A second console runs with a write token that works in the test namespace only; the read-only token for the first browser run is unchanged. The stage then reads the new claim from a pod and checks the files against the data at snapshot time.
- **CDI clones onto a pool are made by the driver.** The pool's CDI StorageProfile now sets `cloneStrategy: csi-clone` instead of `copy`. CDI's host-assisted copy pods (memory limit 600 MB) were killed for lack of memory when they wrote onto NFS: 3 of 3 copies on rovslab, onto a pool and onto IBM VPC File alike. Copying a catalog image from other storage, such as Ceph, onto a pool still uses those pods. They now have a higher memory limit (see below).
- **Golden images are imported by CDI.** The syncer now makes a CDI DataVolume `golden-<image>` in each target namespace, on the pool's StorageClass, with the DataImportCron's registry URL as source (`pullMethod: node`). For ImageStream-based crons (RHEL), it uses the external address the ImageStream imports from. A golden image is ready when the DataVolume phase is Succeeded. On rovslab, CentOS Stream 9 imported in about 40 s and RHEL 9 in about 2.5 min, and VMs booted from both. Catalog entries (DataSources) are now named `<image>-<namespace>-nfs-pool`, one per golden claim. Two pools must not send golden images to the same namespace.
- **Shares use security group access mode.** IBM has deprecated VPC access mode (End of Support 6 May 2027), and the VPC API now refuses new VPC-mode mount targets with HTTP 501, so the driver could not create usable storage on a new cluster. Each share now gets one mount target with a virtual network interface in the worker subnet of the pool's zone, protected by the cluster security group `kube-<cluster ID>`.
- The controller reads every subnet in `vpc_subnet_ids` (and `--subnet-id` accepts a comma-separated list) and picks the one in each pool's zone. It used to take the first subnet, whatever its zone.
- A pool is `Ready` only when at least one share is stable and has a mount target address. Otherwise it is `Degraded`, and the `SharesReady` condition (reason `NoMountTarget`) names the shares. Pools do not add shares while a share is still being created or has no mount target.
- `accessorZones[].subnetID` is now optional and not used: one mount target in the home zone serves every zone.
- `metrics.serviceMonitor.enabled` is now `true` by default. The chart creates the ServiceMonitor only when the cluster has the Prometheus Operator API, so installs on other clusters still work.

### Security
- **Go libraries updated for 13 known advisories (#90).** `google.golang.org/grpc` 1.79.1 to 1.83.1 (up to CVSS 9.1), `golang.org/x/net` 0.48.0 to 0.60.0 (six advisories), `golang.org/x/text` 0.32.0 to 0.42.0 and `github.com/moby/spdystream` 0.5.0 to 0.5.1. The newest `x/net` and `x/text` need Go 1.26, so the project, the build image and CI now use Go 1.26. Whether each advisory could be reached by the driver was not checked.
- **A ReplicationPolicy could run commands as root in `kube-system` (#88).** `spec.rsyncOptions` and `spec.destinationBasePath` were put into the copy Job's shell script without quotes. The webhook now accepts only plain rsync flags (such as `--compress` or `--bwlimit=100`) and an absolute base path of letters, digits, `.`, `_`, `-` and `/`, and the controller quotes every value in the script, so a policy made with the webhook off is safe too. A policy that used a space, quote or `;` in `rsyncOptions` is now refused.
- A user in a target namespace could pre-create the `golden-<image>` DataVolume and have it published to the shared catalog. The syncer now refuses a DataVolume that the pool did not make (missing pool labels, or a different source URL or StorageClass) and publishes no catalog entry for it.
- Pool deletion trusted labels in any namespace. It now removes only objects in the pool's own target namespaces.
- Replication receiver: a tar upload could write files outside the destination volume through a symlink (a sibling directory whose name starts with the destination's name, or a symlinked parent directory). All writes now go through `os.Root`, and symlink targets are checked against the parent's real location.

### Fixed
- **The console's "High-IOPS Database" preset asked for 48,000 IOPS on 4,000 GB shares.** IBM allows 40,000 at that size, so a pool made from the preset would not get its shares. The preset now uses 40,000.
- **`kubectl-migrate` ignored the `KUBECONFIG` variable.** It read only `~/.kube/config`, so it failed on any machine that sets `KUBECONFIG`. It now uses `--kubeconfig`, then `KUBECONFIG`, then `~/.kube/config`, and says so when none exists.
- **`kubectl-migrate` reported success when files were missing.** If the file counts of the old and new claim differed, the copy pod only printed a warning and exited with success. The pod now fails, and so does the tool.
- **A drained share never came back into use.** Once a share was marked draining, by a drain request or because the VPC reported it degraded, it stayed draining after the request was removed or the VPC reported it healthy again. It got no new volumes but was still billed. A healthy share that is not on the drain list is now back in use.
- **Replication failures could go uncounted, so a failing policy never paused.** A cycle was judged only when all its copy Jobs had finished at once, but a volume whose Job finished early got a new Job on the next check. With Jobs that finish at different times, that moment might never come. A volume's result is now kept until every volume of the cycle has finished.
- While a new copy ran, or after one failed, the policy status dropped each volume's last good sync time. It now keeps it, so the age of the last good copy stays visible.
- The replication controller read pods through the shared cache, which needs a `watch` permission the controller does not have, so the running-VM check could fail. It now reads directly.
- The FileSharePool webhook allowed `expandThresholdPercent` 1–99 and `maxShares` up to 1000, but the CRD schema allows 50–95 and up to 100. The webhook now uses the schema's ranges, so its messages give the real limits.
- **VMs made from a golden image template could not get a boot disk.** The template always asked for a 15 GB boot disk, but a copy cannot be smaller than its source, and CDI makes a disk a little larger than requested. The golden disk is now exactly the pool's `pvcSizeGB`, and the template's boot disk defaults to the same size.
- **A pool with golden images could not be deleted.** The syncer made the golden disks again while the pool was being deleted. Deleting a pool now deletes its golden DataVolumes, claims and Templates in its target namespaces, and its DataSources, before the pool. The syncer skips pools that are being deleted.
- **The catalog showed stale or missing golden images.** Catalog entries stayed after their pool was deleted, and every entry for an image had the same name, so only the first namespace of the first pool got one. Entries are now named per namespace and removed with the pool.
- **Golden images needed `anyuid` in the target namespace.** The converter ran as root in the app's namespace. CDI now does the import, so no extra permission is needed.
- **Replication copied the disks of running VMs, and the copies might not boot.** The copy read the disk while the VM wrote to it, so it mixed data from different moments. The controller now skips any volume that a running or starting VM uses, and the volume's status names the VM pod. Skipped volumes do not pause the policy. A copy during which a VM started is not recorded as a sync. Volumes of stopped VMs replicate as before.
- **Clones needed root permission in the app's namespace.** The clone copy Job ran in the claim's namespace as root, so a clone failed unless that namespace had the `anyuid` permission. Clone copies now run as share data Jobs in the driver's namespace, mount the shares directly, and leave nothing in the app's namespace. Deleting a clone while it copies stops the copy first.
- **Deleting a volume left its data on the share, and snapshots held no data.** The controller has no NFS access, so it skipped every data step and still reported success: a deleted volume's folder stayed (the pool showed the space as free), a snapshot was marked ready with nothing copied, a restore gave an empty volume, and a deleted snapshot removed nothing. Kubernetes Jobs in the driver's namespace now do these steps. A volume's space is given back only after its folder is removed, a snapshot is ready only after its copy, and a restored claim binds only after its copy.
- A retried `CreateVolume` for a clone or restore answered from the existing record, without naming the source. The provisioner rejected that answer and tried to delete the new volume. Retries for clones and restores now go to the pool manager, which checks the copy and names the source.
- A retried `CreateVolume` for a volume that already exists returned the share path `/` and no owner or permissions. If the provisioner built the PV from that answer, the volume could not mount, and a KubeVirt volume would get the wrong owner. The answer now matches the first one.
- The console plugin's pool create page offered a `custom` profile, which VPC file shares do not have, so such a pool never got a share. ## [v0.1.0] — 2026-02-15

### Added

- **CSI Controller** (`pkg/driver/controller.go`) — gRPC server implementing `CreateVolume`, `DeleteVolume`, `ValidateVolumeCapabilities`, `ControllerExpandVolume`, and capability RPCs; delegates all allocation logic to the Pool Manager
- **CSI Node Agent** (`pkg/driver/node.go`) — `NodeStageVolume` mounts NFS shares once per node, `NodePublishVolume` bind-mounts subdirectories into pod paths, with mount caching to avoid redundant NFS mounts
- **Pool Manager** (`pkg/pool/manager.go`) — core allocation engine with `Allocate()` and `Deallocate()` methods; supports `spread` (most free space) and `binpack` (least free space) share selection strategies; tracks share capacity via SubVolume CRs
- **FileSharePool reconciler** (`pkg/pool/reconciler.go`) — controller-runtime reconciler watching FileSharePool CRs for background pool management: creates initial shares, handles auto-expansion when utilization exceeds threshold, and updates pool status
- **IBM VPC API client** (`pkg/ibmcloud/client.go`) — thin wrapper around `vpc-go-sdk` for file share CRUD, mount target management, and share capacity expansion; all operations idempotent with context-based timeouts
- **FileSharePool CRD** — cluster-scoped custom resource defining pool configuration: zone, profile, share size, max shares, allocation strategy, auto-expansion, and tier definitions
- **SubVolume CRD** — cluster-scoped custom resource tracking individual PVC allocations: share reference, subdirectory path, requested size, and pool membership
- **Helm chart** (`charts/ibm-vpc-file-pool-csi/`) — deploys controller Deployment, node DaemonSet, CSI sidecars (provisioner, resizer, registrar, liveness probe), RBAC, and StorageClass
- **Storage-secret-sidecar integration** — automatic IBM Cloud API key injection on managed ROKS/IKS clusters using `armada-storage-secret` sidecar
- **Path validation** — all subdirectory operations validate against `^/pvcs/pvc-[a-f0-9-]{36}$` regex and reject path traversal attempts
- **Leader election** — controller uses controller-runtime leader election to prevent concurrent pool state corruption

### Fixed

- VPC API endpoint construction for production IBM Cloud regions
- RBAC permissions for FileSharePool and SubVolume CR watch/update
- Subdirectory creation race condition during concurrent `NodePublishVolume` calls
- Mount target IP resolution when share has multiple mount targets across zones
- Makefile targets for end-to-end build pipeline
