    Spec: Release v0.15.0¶

    Date: 2026-10-27. Status: draft for review.

    Goal¶

    Release v0.15.0 and put it on the three lab clusters: rovslab-dr-eude, rovslab-prod-eude and rovs-aug-2026-v2. After the update, the release test (make test-release) passes on rovslab-prod-eude.

    "Done" means: - The tag v0.15.0 exists, and the images driver, browse and console-plugin at v0.15.0 are in de.icr.io/ibm-vpc-file-pool-csi. - Each of the three clusters runs v0.15.0 for the driver and the console plugin. - The release test passes on rovslab-prod-eude, or each failure has a reason written down. - Every cluster can go back to the version it had before, with one command.

    What is in it¶

    Fifty changes since v0.14.3. Two matter to a person who runs the driver:

    1. Copies of running VM disks adapt their speed. This covers replication, backup and snapshot copies. A copy starts at 15 MB/s, speeds up while the share the VM reads is quiet, and slows down (never below 15 MB/s) when the share is busy. In a lab backup this took 1,410 s, where the fixed 20 MB/s took 1,635 s.
    2. PoolBench, a storage performance test in the console. It is off by default (poolBench.enabled), so a cluster that does not turn it on sees no change from it. DR has it on.

    Smaller: a PoolBench run from before a rule change can now be cleaned up, and a flaky receiver test is fixed.

    Why v0.15.0 and not v0.14.4¶

    • It adds features: PoolBench, adaptive copy speed.
    • It adds a new resource kind (PoolBench) and new fields on BackupPolicy and ReplicationPolicy.
    • It changes a default. The fixed 20 MB/s copy speed is gone for adaptive copies. vmCopySpeedLimitMBps is now the highest speed, and unset means no highest speed. A person who relied on 20 MB/s as a ceiling must set it.

    What changes on a cluster¶

    • New CRD and fields. The CRDs change in an additive way. They must be applied before or with the Helm upgrade (kubectl apply --server-side -f config/crd/).
    • New objects from the chart. A service account <release>-node-reader that can only read the node agents' /metrics; a Role that lets the controller list the node agents' endpoint slices and ask for a token of that one account; a ConfigMap <release>-node-ca that OpenShift fills with the CA. Without OpenShift's service CA, copies stay at the old fixed speed.
    • New controller flags (--node-metrics-service, --node-metrics-account, --node-metrics-ca). The chart sets them.
    • Running copies. The controller restarts in the upgrade. As in earlier releases, a copy in progress is picked up again or restarted by the next cycle. We check that on prod after the upgrade.

    Steps¶

    1. Prepare the release (no cluster is touched)¶

    1. Run /docs-audit and fix what it finds.
    2. One pull request that:
    3. moves the Unreleased items in CHANGELOG.md under ## [v0.15.0] — 2026-10-27;
    4. adds "Upgrading to v0.15.0 (from v0.14.3)" and the compatibility row to docs/UPGRADE-GUIDE.md (new CRD, new chart objects, the changed default, what to check);
    5. sets version and appVersion in charts/ibm-vpc-file-pool-csi/Chart.yaml to 0.15.0.
    6. Squash-merge it. Tag the merge commit v0.15.0 (annotated) and push the tag.

    2. Build and push¶

    On the build server, from the tagged commit: build driver, browse and console-plugin with VERSION=v0.15.0 and push all three. Check each tag exists in the registry. (An earlier release missed browse.)

    3. DR first¶

    rovslab-dr-eude already runs the same code as a main build (v0.14.3-50-g77bdeb2b, rev 67). Apply the CRDs, then upgrade to v0.15.0 for both the driver and the console plugin. Check: pods roll out; the start-up line shows version=v0.15.0; no "Cannot read the latency" line in the controller log; PoolBench still works (start a Quick check and let it pass).

    4. Production (needs your go-ahead)¶

    rovslab-prod-eude is on v0.14.3 (rev 47). It holds the kept namespace ovl-test (VMs ovl, ovl-r, win). Before: list the pools and copies in progress. Apply the CRDs, upgrade both images. After: every pod ready; every VM still running; node /metrics answers HTTP 200 on all nodes; one replication policy or backup shows vmCopy.speedMBps moving; ovl-test untouched.

    5. Release test (needs your go-ahead)¶

    Run make test-release CLUSTER=rovslab-prod-eude on the build server. It runs about as long as the earlier runs. It needs the cluster to itself, so nothing else may run on prod. Read the report; fix or file each failure.

    6. rovs-aug (needs your go-ahead; the cluster runs other people's VMs)¶

    Upgrade only after steps 4 and 5 are green and you say yes. The same checks as in step 4. Rollback is rev 15.

    Going back¶

    Cluster Now Go back with
    rovslab-dr-eude rev 67 (main build) helm rollback ibm-vpc-file-pool-csi 67 -n kube-system
    rovslab-prod-eude rev 47, v0.14.3 helm rollback ibm-vpc-file-pool-csi 47 -n kube-system
    rovs-aug-2026-v2 rev 15, v0.14.3 helm rollback ibm-vpc-file-pool-csi 15 -n kube-system

    The CRD changes are additive, so the older driver still works with them. A policy that leaves vmCopySpeedLimitMBps unset runs at 20 MB/s on the older driver, as before.

    Risks¶

    • The copy speed is new on prod. It was tested on DR with one VM and a small run. If a VM slows down on prod, set vmCopyAdaptive: false on the policy to go back to a fixed speed without a rollback.
    • PoolBench on prod stays off. We do not turn it on there in this release.
    • Not tested on a cluster: the snapshot copy speed (the lab takes instant snapshots, which copy nothing) and the speed change on a Windows VM (QEMU does the change, so we do not expect a difference).

    Cost¶

    About two hours of work, plus the release test run (hours, unattended). The clusters are used as they are; nothing new is created.

    Decisions I made for you¶

    • The version is v0.15.0, not v0.14.4, because of new features, a new resource and a changed default.
    • DR goes first, then prod, then the release test, then rovs-aug last.
    • PoolBench stays off on prod and rovs-aug in this release.
    • I will not touch prod, run the release test, or touch rovs-aug without your yes for each.
    • The release test runs on prod, as in earlier releases, and not on DR.
    • Rollback is a Helm rollback to the revision now on each cluster. I do not remove the new CRD fields.
    • browse is built and pushed with the other two images, because an earlier release missed it.
