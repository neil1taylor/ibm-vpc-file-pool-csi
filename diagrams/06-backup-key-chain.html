The Backup Key Chain

Backups sent to IBM Cloud Object Storage (COS) are locked with a backup key. That key is never stored as it is. Key Protect, an IBM Cloud service, locks it with its own root key. This page follows each key from setup to a backup and a restore, then asks what happens when one is lost. All key names here are made up. No page, log or status of the driver shows a real key.

Where each key is kept

RK: the root key, never leaves Key Protect B: the readable backup key W: B locked by RK (wrapped) A: the Key Protect API key C: the key for the one bucket the backups new in this step

What if something is lost?

Press a button to break something. Press it again to repair it. The two boxes below say what still works.

Who can open what

KeyWhat it opensIf it is lost
RK root key (Key Protect)Locks and unlocks W. Nobody can read it, not even you.If it is deleted, W can never be unlocked again. Only the emergency key file can read the backups. The Jobs get a refusal and stop.
W wrapped key (bucket and a cluster Secret)Nothing alone. It is B, locked.One copy is enough, because the bucket and the cluster each hold one.
B readable backup keyOpens every backup of the policy. Lives only in a Job's memory, and in your emergency copy.Not stored by the driver, so it can always be made again from W while Key Protect works.
Emergency key file (B, kept by you outside IBM Cloud)Restore with --backup-key-file. Key Protect is not called.Nothing happens while Key Protect and RK are fine. If they are lost as well, nobody can read the backups.
A Key Protect API key (cluster Secret)Lets the driver ask Key Protect to unlock W. It has the Reader role on RK only.If its access is removed, exports and clean-up stop. Anyone who can read this Secret can ask Key Protect to unlock W, as the driver does, so guard it like the key.
C bucket key (cluster Secret)Writes to the one bucket. It cannot delete versions, skip a lock or change bucket settings.Delete its HMAC key in IBM Cloud and run kubectl backup cos-setup again for a new one.

Decided by the code: the emergency key is used only when Key Protect cannot be reached. If Key Protect answers with a refusal (a wrong root key or a bad API key), the Job fails. It never hides a setup mistake. The controller never reads these keys and never calls Key Protect: only the Jobs do.

What is proven: with a real Key Protect root key in the lab (eu-de), export and restore from COS worked, and the VM booted with matching checksums. Not yet proven: restore with the emergency key file, and a restore in the DR cluster. Do not treat the COS copy as your only backup until they pass.
