    Features¶

    Overview¶

    The IBM VPC File Pool CSI Driver replaces the traditional one-PVC-per-share model with a pooled architecture: a small number of large VPC file shares are pre-provisioned, and each PVC gets a subdirectory on an existing share. This eliminates the 30-90 second wait for VPC share creation, reduces the number of shares needed (VPC accounts cap at 300), and consolidates billing since each share has a 10 GB minimum.

    For cluster administrators, the driver manages pool lifecycle automatically — expanding capacity when usage crosses a threshold, monitoring share health via the VPC API, and draining degraded shares without manual intervention. State lives entirely in Kubernetes CRDs (FileSharePool, SubVolume, Snapshot), so there is no external database or ConfigMap to manage.

    For workload teams, the driver is invisible: they create standard PVCs and the CSI sidecar routes requests to the pool manager. PVC creation completes in under a second. Volume snapshots, clones, and group snapshots work through the standard CSI interfaces. KubeVirt users get first-class support with correct directory ownership and raw disk image handling.

    The driver is purpose-built for IBM Cloud ROKS and ROVS clusters running on VPC infrastructure. It integrates with the VPC file share API, creates one mount target per share that serves pods in every zone, and authenticates through the same secret-common-lib used by the stock IBM CSI drivers.

    Feature Categories¶

    Core: Pooled Storage Model — GA¶

    Subdirectory-based PVC provisioning on shared VPC file shares. Each PVC maps to a directory (/pvcs/pvc-<uuid>) on an existing share, tracked by a SubVolume CR.

    • CRD-based state — FileSharePool and SubVolume CRDs hold all allocation state. No external database or ConfigMaps.
    • Background reconciliation — VPC API calls (share creation, health checks, mount target discovery) happen in a background reconciler. One exception: with autoExpand on, a CreateVolume that finds no share with room calls CreateFileShare itself and returns a retriable error so the provisioner retries.
    • Instant PVC creation — CreateVolume records a SubVolume CR and returns immediately (<1s vs 30-90s for the stock driver).
    • Idempotent operations — All CSI methods are idempotent with crash recovery. Duplicate requests return the same result.

    Allocation & Capacity — GA¶

    Share selection and capacity management across the pool.

    • Spread strategy — Distributes PVCs evenly across shares for lower blast radius (default).
    • Binpack strategy — Fills shares before using the next one, minimizing active share count.
    • Automatic pool expansion — When allocation exceeds a configurable threshold (default 80%), a new VPC share is created in the background. Proactive expansion adds buffer before the threshold is reached.
    • Per-PVC quota tracking — Each SubVolume records its requested size. Pool capacity accounting prevents overcommit.
    • Configurable reclaim policies — Delete (remove subdirectory on PVC deletion) or Retain (keep data for manual recovery).

    Volume Snapshots — Beta¶

    Directory-level point-in-time copies via the standard CSI snapshot interface.

    • CreateSnapshot — A Job in the driver's namespace copies the SubVolume directory to a snapshot path on the same share. The Snapshot CR reads readyToUse: false until the copy has finished. If a running VM uses the claim, the snapshot is a QEMU copy of that disk at one moment instead (guest frozen for a moment; status.consistency says if it worked; the copy adapts its speed to the load on the share; vmCopySpeedLimitMBps on the VolumeSnapshotClass sets the highest speed, and vmCopyAdaptive: "false" makes it a fixed speed, default 20 MB/s). Experimental, like the VM disk copy for replication.
    • Instant VM disk snapshots — Experimental — Where the KubeVirt Sidecar feature gate is on, a snapshot of a VM disk is a new overlay file and nothing is copied: it is ready in seconds, whatever the disk size, and an OpenShift VM snapshot gives all disks of a VM at the moment OpenShift froze the guest. Deleting a snapshot merges its file back while the VM runs. A webhook gives a VM with snapshots the driver's hook when it starts. Red Hat does not support the Sidecar gate. See VM-INSTANT-SNAPSHOTS.md.
    • DeleteSnapshot — A Job removes the snapshot directory; then the CR is deleted and the pool capacity is given back.
    • ListSnapshots — Lists snapshots filtered by source volume with pagination support.
    • Restore from snapshot — A Job copies the snapshot directory into the new volume and sets the pool's owner and permissions. The claim stays Pending until the copy has finished.
    • Validating webhook — Ensures Snapshot CRs have required fields (sourceSubVolume, poolName).

    Volume Cloning — Beta¶

    Asynchronous, Job-based cloning for every volume size.

    • Async copy — CreateVolume creates a SubVolume CR with CloneStatus=Pending and returns. The clone worker runs a Kubernetes Job that copies the data (the controller pod has no NFS access).
    • Same-share preference — Clones prefer the same share as the source for speed. Falls back to cross-share when capacity requires it.
    • Clone status gate — NodePublishVolume returns Unavailable for SubVolumes with an in-progress clone, preventing pods from mounting incomplete data.
    • Crash recovery — The clone worker recovers incomplete clones on restart by scanning for SubVolumes in Pending/InProgress state.
    • Progress tracking — CloneProgress tracks BytesCopied, TotalBytes, StartedAt, CompletedAt, and Error.

    Backup to a Snapshot Pool — Experimental¶

    One BackupPolicy backs up the volumes and VMs it selects into a pool that holds only backups, so a lost data share does not take the backups with it. Built on replication, so a running VM is backed up at one moment, all disks together, and only changed blocks are copied.

    • Selection — By PVC label and namespace. If any disk of a VM matches, all its disks are backed up.
    • Moments — The latest backup of a VM disk is whole; earlier moments are undo files (restore points). Other volumes keep each sync as a folder of hard links, so an unchanged file takes no extra space. Moments older than keepFor (default 7 days) go.
    • Restore — kubectl backup restore --policy P --pvc NS/NAME --to NS/NEW [--moment TIME] makes a new PVC and copies the backup into it; the volume is held back from pods until the copy ends. It never writes over a volume that exists, and works after the source volume is deleted.
    • More than one share — A snapshot pool may have several shares. A new volume goes to the ready share with room that holds the fewest volumes and stays there; a restore reads from it.
    • Full share — Above 85% full, a share of the snapshot pool gets no new backups and the policy reports Error. The other shares go on, and new volumes avoid the full one. Backups are never deleted to make room; they resume when usage falls.
    • Delete — kubectl backup delete --policy P --pvc NS/NAME removes the backup and all earlier moments of one volume, after a typed confirmation (or --yes). It refuses while the policy still backs up the volume or a restore of it runs, and the controller never runs it.
    • Export to COS (part 2: controller) — With spec.export (bucket, endpoint, prefix, credentials and backup-key Secrets, keepFor default 30d, lock Compliance or None, optional schedule), the controller sends each new backup moment of a volume to a Kopia repository in a COS bucket, one Job at a time for each policy, reading the snapshot pool read-only. Status per volume: exportedTime, exportedBytes, exportError. A maintenance Job extends locks and deletes snapshots older than keepFor. An export problem never stops the backups to the snapshot pool. kubectl backup cos-setup (part 4, run against real IBM Cloud in stage 18) makes the instance, the locked bucket, the write-only role, the key limited to one bucket, the CBR rule and the wrapped backup key, and prints the spec.export block. Key handling (part 3): the backup key is stored only wrapped by Key Protect; the Jobs unwrap it in memory, with an optional emergency key if Key Protect is down (both proved against a real Key Protect root key and a real bucket in stage 18). Restore from COS (part 5): kubectl backup restore --from-cos and kubectl backup cos-list work in a cluster with no policy and no snapshot pool; if Key Protect is gone, --backup-key-file restores with the readable key. Proved in stage 18 against a real bucket, in the same cluster and in the DR cluster, with Key Protect and with the emergency key.
    • Browse the files inside a VM disk backup (issue #92, phase 5, in development) — Without starting the VM, a helper pod runs a small read-only appliance VM (libguestfs) that reads the guest's partitions, LVM volumes and file systems (XFS, ext4, NTFS and more) from a backed-up disk shown to it at any restore point by a read-only disk server. Built: the disk view (byte for byte equal to a whole-disk restore, checked on random histories), the disk server (read-only NBD), the hold that makes the volume's next backup copy wait while a session is open, the guest helper with its image and chart values (off until the image is built), restore of files into a claim, kubectl backup ls/get/restore-files --fs, and the console picker with notices for crash copies and the reasons for volumes that cannot be read. Not run on a real cluster yet. Not yet: VM disks in COS, BitLocker, LUKS and ReFS (only the whole-disk restore reads them). See BACKUP-RECOVERY.md.
    • Browse and restore files from a backup in COS (issue #92, phase 4, Experimental) — kubectl backup ls, get, browse and restore-files read a plain volume's backup from the policy's COS bucket with --from-cos, and the gateway picks COS by itself for a moment that only COS holds. A cluster administrator can name a bucket directly. The reader runs the pinned Kopia program read-only as a child process, unwraps the backup key in memory, walks folders by object IDs read from the repository (a user's path never reaches Kopia, a link leads nowhere) and uses only the snapshots of the one volume, so other volumes in the bucket area stay out of reach. Its pod is in the driver namespace, has no service account token and runs as an ordinary user; the keys are never copied to the browse namespace. Failures of Key Protect and COS are said in words. Not yet: VM disks in COS, a source switch in the console, and a fast path for thousands of small files (each file is one run of Kopia). See BACKUP-RECOVERY.md.
    • Restore files from a backup, part 5: kubectl backup restore-files (issue #92, Experimental) — Users restore chosen files and folders of a plain-volume backup into a new claim or a new folder of an existing claim with kubectl backup restore-files, through the gateway. The gateway checks the user's own token and, on every call, get backupfiles in the namespace of the backed-up claim, create on claims in the target namespace and, for an existing claim, update; it takes the existing claim's UID so a claim made again is refused, shows a restore only to the user who asked, and writes an audit Event with the user and the paths. See BACKUP-RECOVERY.md.
    • Restore files from a backup, part 4: BackupFileRestore (issue #92, Experimental) — A cluster administrator can copy chosen files and folders out of a backup of a plain volume (snapshot pool) into a new claim, sized to the files plus 20%, or into a new folder of an existing claim, at the latest copy or at a moment. Nothing is written over a file that exists, nothing goes into a VM disk, links are copied as links and never followed, and setuid bits are removed. The owner is the one the pool configures for the claim. The Job checks the space first, writes a hidden folder and renames it at the end, and a failed try leaves nothing. Not yet: users cannot ask for it (the gateway and kubectl backup restore-files come next), the console, COS backups, VM disks. See BACKUP-RECOVERY.md.
    • Restore chosen files in the console (issue #92, phase 3 second half, Experimental) — In the file browser, tick files, folders and links (the line above the table counts them and adds up the file sizes; a folder comes with everything in it and a link stays a link), press Restore selected, and a dialog restores them into a new claim (the default; size and storage class can be set, otherwise the driver measures the files and adds 20%) or into a new folder of an existing claim. It states what will be written and that nothing is overwritten, turns off the existing-claim choice with the missing rights named, follows the phases (Pending, Measuring, Provisioning, Restoring, Done or Failed) with short requests, and ends with links to the claim, the folder, the counts and the size. A refusal is explained in plain words (which right is missing; the name is taken, with another suggested; too many open restores). It uses the gateway calls of phase 2 and the user's own token only. Not yet: COS backups, VM disks. See BACKUP-RECOVERY.md.
    • Browse and download files in the console (issue #92, phase 3 first half, Experimental) — A Browse files action on each volume of a backup policy opens a file browser: folders in pages of 1000, breadcrumbs, a picker for the latest copy or any moment, sizes and times, and a download of one file or of a folder as a tar. A symbolic link is shown with its target and never followed or downloaded; a file the reader cannot open is marked "Not readable"; names are always shown as escaped text, the same as kubectl backup ls. The page starts a session, polls it with short requests, and closes it when you leave. Downloads are plain links through the console plugin proxy, which adds your own token (the browser holds nothing else and no token is in a link); the gateway has a new GET download route and sets Content-Disposition: attachment, nosniff and a sandbox policy on every file and tar reply. The chart adds the proxy entry and a fileBrowse flag to the settings ConfigMap. Restoring chosen files is in the entry above. Not yet: COS backups, VM disks. See BACKUP-RECOVERY.md.
    • Browse a backup, part 3: gateway and kubectl backup ls/get/browse (issue #92, Experimental) — Users list and download files and folders of a plain volume's backup (snapshot pool), at the latest copy or at a moment, with kubectl backup ls, get and browse. The backup gateway checks the user's own token and, on every call, the right get backupfiles in the namespace of the claim; the built-in admin role has it with no setup (backup-file-reader is aggregated into it); other people need a RoleBinding. Calls to the helper pod are encrypted and trust only that session's certificate. Each session start, download and close is an audit Event with the user and the path. Helper pods and session Secrets live in their own namespace, which holds nothing else. Not yet: restoring files into a claim, the console pages, COS backups, VM disks. See BACKUP-RECOVERY.md.
    • Browse a backup, part 2: sessions (issue #92, in development) — A BackupBrowse resource (cluster scoped; only the gateway will make it) and the controller part: for each session a Secret with a token and a per-session TLS certificate, and a helper pod that mounts only that volume's backup read-only, with limits (15 minutes idle, 2 hours hard, 5 open in the cluster and 2 for each namespace), clean-up after a restart, and every object tied to the session's UID. See BACKUP-RECOVERY.md. Still nothing a user can run: the gateway and kubectl backup come next.
    • Browse a backup, part 1 (issue #92, in development) — The helper that will read one backup folder for the browse feature is built and proven on a real share, but nothing in the driver starts it yet: no command, console page or resource uses it. It runs as root with every capability dropped on a read-only mount, never follows a link (openat2 with RESOLVE_BENEATH and NO_SYMLINKS), keeps names as raw bytes, and serves list, stat, file range and tar over HTTP with a session token. It ends by itself when idle (15 minutes) or after 2 hours. On the lab share it read another user's files with mode 0600 and folders with mode 0700. The next parts add the BackupBrowse resource, the gateway with Kubernetes access checks, kubectl backup ls/get/browse, and file restore. See BACKUP-RECOVERY.md.

    PoolBench — Experimental¶

    A storage performance test that the console will start, show live and control (docs/specs/2026-10-25-poolbench.md). A PoolBench resource holds every setting; the PoolBench service (Helm poolBench.enabled, off by default) makes the run's own namespace and pool, adds test VMs in steps (Linux and Windows, the load of the command-line test in test/perf), measures each step, finds the knee, and cleans up. Pause, hold, measure longer, skip and stop work through spec.control. Run on the DR lab cluster, where the 3,000 IOPS result matched the command-line test.

    Volume Group Snapshots — Not active¶

    The code and the record type exist, but nothing acts on a VolumeGroupSnapshot record, the hooks never run, and the console no longer shows it. There is no plan to turn it on (issue #100). A running VM with several disks does not need it. What the code was built to do:

    • Coordinated snapshot creation — CreateVolumeGroupSnapshot takes a list of PVCs and snapshots them in order, tracking per-member state (Pending, Creating, Ready, Failed).
    • Failure policies — Abort (default) rolls back completed snapshots on first failure. Continue finishes all members and marks the group as PartialFailure.
    • Copy order — Configurable ordering of member snapshots. Defaults to alphabetical PV name sorting.
    • Inconsistency window tracking — Measures the time delta between first and last member copy in milliseconds.
    • Pre/post-snapshot hooks — Exec and HTTP webhook hooks via the hook orchestrator for application quiescing.
    • Validating webhook — Ensures VolumeGroupSnapshot CRs have poolName and sourcePVCs.

    Cross-Region Replication — Beta¶

    Disaster recovery with configurable sync schedules. Two replication modes are supported.

    • Direct NFS mode — rsync-based replication between source and destination NFS shares mounted over Transit Gateway or VPN. Uses incremental delta transfer for efficiency.
    • Driver-to-driver mode — HTTPS-based replication from sync-client Jobs on the source cluster to a receiver service on the destination cluster. Streams tar archives over HTTPS with bearer token auth. No cross-region NFS connectivity required.
    • Schedule-based sync — ReplicationPolicy CR defines sync interval (e.g., 15m, 1h, 6h) as a duration string.
    • Per-SubVolume incremental sync — Optional label selector filters which SubVolumes replicate. Incremental mode (default) uses rsync for efficient delta transfer (direct NFS mode).
    • Bandwidth limiting and parallel syncs — bandwidthLimitMbps caps rsync throughput (direct NFS mode); maxParallelSyncs controls concurrent SubVolume syncs in both modes.
    • Extra rsync options — rsyncOptions field passes additional rsync flags (e.g., --compress, --checksum). Dangerous flags (--daemon, --server, --rsh, --rsync-path) are blocked by the webhook. Only applies to direct NFS mode.
    • Retry with backoff — Configurable max retries (default 3). Policy pauses on consecutive failures.
    • Running VM disks — Experimental — The controller copies a running VM's disks with QEMU, all at one moment, after a short guest freeze (0.15 s in a lab test). After the first copy, each copy holds only the changed blocks. The destination saves the old contents of every changed block first, so a copy that stops half way is rolled back, and it keeps those as restore points for 24 hours by default (restorePointKeepHours). The copy is file-system consistent, or crash consistent if the guest cannot freeze, and the status says which. The copy adapts its speed: it starts at 15 MB/s for each disk, speeds up while the share the VM reads is quiet, and slows down when that share's latency passes 15 ms (vmCopyAdaptive, vmCopyMaxLatencyMs; the node agents' metrics are needed, otherwise it runs at a fixed speed). A live migration cancels the copy. In receiver mode the receiver at the destination applies each copy, and after a VM move only the blocks that differ are sent. Tested between two clusters with Linux and Windows Server 2022 VMs (freeze, copy, rewind and boot). Red Hat does not support the QEMU commands this uses.
    • Pause/resume via annotation — Annotate a ReplicationPolicy with storage.ibmcloud.io/paused=true to pause; remove the annotation to resume. The controller updates status.phase accordingly.
    • Pre/post-sync hooks — Exec and HTTP hooks for application quiescing before sync and notification after.
    • Metadata sidecar — Writes .subvolume-metadata.json alongside each replicated SubVolume directory, enabling the failover CLI to reconstruct resources without querying the source cluster.
    • Failover CLI — kubectl failover plugin with plan (scan destination NFS, compute RPO), execute (create SubVolume CRs, PVs, PVCs on DR cluster), and status (report PVC binding) subcommands. For running VMs it picks the newest moment all of a VM's disks can show, rolls back a copy that stopped half way, and with --rewind-to goes back to an earlier restore point (--list-moments lists them). Supports --dry-run and is idempotent.
    • Failover resource — Experimental — A cluster-scoped Failover resource plans or carries out a failover on the destination cluster without a shell. A Job in kube-system mounts the destination claim (by default the receiver's data claim) and runs the same code as kubectl failover; the result goes into the resource's status (VMs, the moment each will show, the moments to choose from, which disks must be rewound, the RPO). action: Execute also makes the SubVolume, PV and PVC objects. The share address comes from the volume behind the claim: an NFS volume, or a claim the driver provisioned (its server, share and subDir attributes); spec.drShareIP and spec.drExportPath override it. spec.basePath names the folder of the claim that holds the copies (the policy's destinationBasePath, default /); a Plan with no pvcs folder or no replicated volume there fails and says where it looked. spec.vms limits a Plan or Execute to chosen VMs (all disks of a VM come together; plain volumes are left out); empty means every VM on the copy. An Execute is refused unless a Plan for the same source, rewindTo and VM list (spec.vms) finished in the last 15 minutes, the share still gives the same plan, and the VM was not failed over on this cluster before. Only cluster admins can create one (the failover-admin ClusterRole is bound to nobody by default). The policy page in the console shows, for each running VM, the copy moment, whether it is file-system or crash consistent, the moments all its disks can show (status.vms[].commonMoments) and a warning when the newest copy is older than twice the schedule (read-only). The console also has a Recovery page under Replication: it plans a failover, shows each running VM with its disks and moments (a disk that must be rewound says it copies the whole disk), and fails over one VM at a time ("Fail over this VM" makes a Plan and an Execute for that VM only) or, with an explicit "Fail over all VMs" button, every VM on the copy. A confirm dialog lists the moment, the disks to rewind and the PVCs to be made, and needs the VM name (or the source name for all VMs) typed. It shows progress, the created PVCs and the Failover message, and offers force only behind an extra warning when a copy is being applied. It uses the signed-in user's rights, so the user needs the failover-admin role.
    • Status tracking — Per-policy LastSyncTime and LastSyncDuration. Per-SubVolume sync state with BytesSynced and LastError.
    • Destination config — NFS server IP and base path (direct NFS mode), or HTTPS receiver endpoint with bearer token auth (driver-to-driver mode).
    • Prometheus metrics — Dedicated metrics for sync total, duration, lag, failures, and SubVolume count.

    NFS & Mount Management — GA¶

    Efficient NFS mount handling with security enforcement.

    • Mount reuse — One NFS mount per staged volume. A second pod on the same volume reuses the mount. A different volume on the same share is mounted again.
    • Bind-mount publishing — NodePublishVolume bind-mounts the SubVolume's subdirectory from the staged NFS mount into the pod's volume path.
    • sec=sys enforcement — All NFS mounts include sec=sys to ensure proper UID/GID authentication. Without it, VPC shares negotiate sec=null and all files appear as UID 99.
    • Soft mount defaults — Mount options nfsvers=4.1,soft,timeo=600,retrans=3 prevent pods from hanging on NFS failures.
    • Mount target address — Each share has one mount target, in the pool's zone. Nodes in every zone mount it.
    • Path traversal validation — All subdirectory paths validated against ^/pvcs/pvc-[a-f0-9-]{36}$ before any filesystem operation.

    KubeVirt Integration — Beta¶

    First-class support for running virtual machines on pooled storage.

    • UID 107 directory ownership — Pool defaultUID: 107 and defaultGID: 107 ensure subdirectories are pre-owned for QEMU (virt-handler chowns to 107:107).
    • Raw disk image support — KubeVirt requires raw format for filesystem PVCs. Cloud images (distributed as qcow2) must be converted to raw. CDI does this when it imports an image, and the pool's golden images (a Hidden feature) are made by CDI. Convert with qemu-img convert -f qcow2 -O raw only if you write images to a pool yourself.
    • CDI registry import — CDI imports an image from a registry onto a pool StorageClass. This was measured on rovslab (CentOS Stream 9 in about 40 s, RHEL 9 in about 2.5 min). A copy of a catalog image from other storage (such as Ceph) onto the pool uses CDI's copy pods. Their default memory limit is too small, so the controller raises it (see the CDI copy limit feature below).
    • sec=sys enables chown — With sec=sys, virt-handler's chown to UID 107 succeeds. Without it, chown fails for all non-root UIDs.

    Multi-Tenancy & Performance Tiers — Beta¶

    Multiple independent pools with per-tier storage profiles.

    • Multiple pools per cluster — Each FileSharePool CR is independent with its own shares, capacity, and allocation strategy.
    • Tiered storage — Pools can define multiple ShareTiers, each with a distinct IOPS value, share size, and max share count.
    • Auto-generated StorageClasses — Non-tiered pools generate one StorageClass ({pool-name}). Tiered pools generate one per tier ({pool-name}-{tier-name}). Skip with the storage.ibmcloud.io/skip-storageclass annotation.
    • Tier-aware allocation — CreateVolume requests pass the tier name via StorageClass parameters. Share selection filters to the requested tier.
    • Resource group & tag support — Shares can be tagged with VPC resource group and user-defined tags for cost tracking.

    Pool Lifecycle & Resilience — GA¶

    Automated pool management with health monitoring and safe shutdown.

    • Pool phases — Initializing (no shares ready) → Ready (stable capacity) → Expanding (creating shares) → Degraded (draining/unhealthy shares) → Full (at max capacity).
    • Share health monitoring — Background reconciler polls VPC API for share lifecycle state. Promotes creating shares to stable when mount targets are available. Detects VPC-reported degradation.
    • Share draining — Marking a share for drain excludes it from new allocations. ShareDrainStatus tracks remaining SubVolumes and drain start time. Share is removed when empty.
    • Pool finalizer protection — Pools cannot be deleted while SubVolumes exist.
    • Leader election — Single-writer safety for the controller. Concurrent controllers would corrupt pool state.
    • Crash recovery — All state in CRDs. Controller restart re-reads CRs and resumes from last known state.

    IBM VPC Platform Integration — GA¶

    Thin wrapper around the VPC file share API with operational guardrails.

    • VPC file share CRUD — Create, get, list, delete shares with idempotent retry. All operations use context-based timeouts.
    • Mount target management — Creates one mount target per share, in the pool's zone. Tracks its IP address.
    • API rate limiting — 5 requests/second default to stay within VPC API limits.
    • secret-common-lib authentication — API key and pod identity auth via the same library used by the stock IBM CSI drivers. Runs as a sidecar with panic recovery.
    • Config auto-discovery — Reads cluster zone, resource group, and VPC ID from standard IBM Cloud ConfigMaps.
    • Initial owner handling — Sets initial_owner: {uid: 65534, gid: 65534} on share creation so root (squashed to 65534 by NFS root_squash) can manage the share root.

    Security — GA¶

    Defense-in-depth controls for a storage driver running with host access.

    • Path traversal validation — All mkdir/rm operations validate paths against ^/pvcs/pvc-[a-f0-9-]{36}$ and reject traversal attempts.
    • Validating admission webhooks — Beta — Nine validating webhooks cover the CRD types (FileSharePool, SubVolume, Snapshot, VolumeGroupSnapshot, ReplicationPolicy, BackupPolicy, BackupRestore, PoolBench, Failover). A mutating webhook adds the VM hook to VMs with instant snapshots.
    • RBAC minimal permissions — Controller and node service accounts use least-privilege roles.
    • No secrets in logs — API keys and tokens are never logged. Share IDs and mount target IPs are safe to log.

    Observability — GA¶

    Prometheus metrics and structured logging for operational visibility.

    • Prometheus metrics — 37 metrics covering allocation (count, duration, capacity, size and allocation of each share), VPC API calls (count, latency), snapshots, clones, group snapshots, replication, and backups.
    • Structured logging — klog/v2 with InfoS/ErrorS and key-value pairs. V(2) for normal operations, V(4) for detailed flow, V(6) for trace-level.
    • Key metrics:
    • vpc_file_pool_allocations_total — allocation/deallocation counts by pool and status
    • vpc_file_pool_allocation_duration_seconds — allocation latency histogram
    • vpc_file_pool_capacity_gb / vpc_file_pool_allocated_gb — pool utilization gauges
    • vpc_file_pool_api_calls_total / vpc_file_pool_api_call_duration_seconds — VPC API health
    • vpc_file_pool_snapshots_total / vpc_file_pool_clones_total — data protection operation counts
    • pool_csi_replication_lag_seconds — replication RPO monitoring

    Deployment — GA¶

    Production-ready packaging for ROKS and ROVS clusters.

    • Helm chart — Full customization via values.yaml. Configurable image tags, resource limits, node selectors, tolerations, and all driver parameters.
    • ROKS/ROVS kubelet path handling — ROKS and ROVS use /var/data/kubelet (not /var/lib/kubelet). The chart's node.kubeletDir defaults to the correct path.
    • UBI9-based container image — Built on Red Hat Universal Base Image 9 for enterprise compliance.
    • cert-manager webhook TLS — Admission webhooks use cert-manager for automatic certificate provisioning and rotation. ROVS has no cert-manager; on ROKS and ROVS set webhook.certProvider=openshift (see INSTALL.md — Webhook Certificates).
    • hostNetwork for NFS persistence — Node DaemonSet runs with hostNetwork: true so NFS TCP connections survive container restarts.

    Migration — Beta¶

    CLI tool for migrating PVCs from the stock IBM VPC File CSI driver.

    • kubectl migrate plan — Discovers PVCs in a namespace by StorageClass, calculates total size, detects pod attachments.
    • kubectl migrate execute — Creates a migration pod that copies data from the source PVC to a new SubVolume in the target pool.
    • kubectl migrate status — Checks migration pod progress.
    • Migrate volumes in the console — A "Migrate volumes into a pool" link on the Pools tab opens a page that lists the claims of another storage class, refuses a claim a pod uses or a move that does not fit the pool, asks for confirmation, and then makes the same new claim and pod as kubectl migrate execute. It follows the copy and never deletes the old claim. See TUTORIAL-08-MIGRATION-AND-CONSOLE.md.
    • Receiver setup in the console — The replication form, in Driver-to-Driver mode, makes the token and CA Secrets from what you paste, runs a short check Job in the source cluster (the address answers, the certificate is trusted, the token is accepted), and turns Create on only when it passes. See CROSS-REGION-DR.md. Afterwards the controller keeps checking the receiver and shows "Reachable" or the reason it is not on the policy list and page.
    • Dry-run mode — Preview migration plan without making changes.
    • Idempotent and resumable — Safe to re-run after interruption.

    OpenShift Console Integration — Beta¶

    Visual management of file share pools through the OpenShift Console.

    • Dynamic console plugin — Registers as an OpenShift ConsolePlugin (v1 API, requires OpenShift 4.14+). On by default where the cluster has the OpenShift console; the chart turns it on in the console. Turn it off with consolePlugin.enabled=false.
    • Single tabbed navigation — One "IBM VPC File Pools" item under Storage in the console sidebar opens a tabbed interface (Overview, Pools, SubVolumes, Snapshots, Replication, Backups, Monitoring, PoolBench). Detail and create pages render standalone without tabs.
    • Pool dashboard — Overview tab showing all FileSharePools with status, capacity gauges, share count, SubVolume count, and recent activity table.
    • CRUD for 4 CRDs — List, detail, create, edit, and delete views for FileSharePool, SubVolume, Snapshot, and ReplicationPolicy resources. Create buttons route to custom form wizards (not the YAML editor).
    • FileSharePool creation wizard — 6-step guided wizard for creating pools: zone/profile selection, capacity configuration, allocation strategy, directory ownership, and review. The form no longer offers golden images.
    • IOPS column in pool table — Displays spec.iops, or "VPC default" when it is not set.
    • Restore a snapshot to a new PVC — A "Restore to new PVC" action on the snapshot details page and in the list row menu opens a form (name, size, storage class, access and volume mode) and creates a claim whose data source is the snapshot's VolumeSnapshot. A banner follows the copy. It never replaces an existing volume. See BACKUP-RECOVERY.md.
    • Clone a volume to a new PVC — A "Clone to new PVC" action on the SubVolume details page and in the list row menu opens the same kind of form and creates a claim whose data source is the volume's claim. The same banner follows the copy. It never changes the source volume. See VOLUME-CLONING.md.
    • Backups in the console (issue #46) — A "Backups" tab lists each backup policy (snapshot pool, schedule, keep time, phase, volumes, stalest backup, export on or off). A policy page shows its settings and one row for each volume: newest and oldest backup, restore points, size, consistency, error and export state. A banner says in plain words when new backups are stopped because the snapshot pool is more than 85% full, and links to the pool. A Restore action on each volume opens a page that restores the latest backup, or the newest one at or before a chosen time, to a new claim (it never overwrites a volume), asks for confirmation, and follows the restore to Done or Failed. Create, edit, suspend, resume and delete a policy are in the console too (a form that checks the pool, the schedule, the keep time and the labels, and counts the claims the labels match). A Delete backups action on each volume measures the backups with a Job, shows the size and the number of moments, asks you to type the claim, and then removes them with a Job; it refuses while the policy still backs up the volume or a restore of it runs. The Job specs are tied to the Go ones by a golden file. A COS tab shows the export settings and the export state of each volume, and lists what is in the bucket with a read-only Job. Restore from COS makes a BackupRestore from a bucket, in any cluster that runs the driver. A guide in the COS tab sets up the export as far as a browser can: it shows the cos-setup command with your names filled in (the console cannot run it, because it has no IBM Cloud login), makes the Secrets from the pasted manifests, writes the pasted spec.export into the policy, and shows whether the export works. See BACKUP-RECOVERY.md.
    • PoolBench tab (in development) — Lists the performance test runs (share, state, VMs now, knee, recommended count, start, run time; a failed run says why). A run page shows a live status line ("Step 3 of 6: 45 VMs running (15 Windows), measuring, 20 min left") and the expected end, the result in one sentence, an HCIBench-style table with one row per step (share, guest and IBM IOPS with the percent of the share limit, share latency, p50, p95 and p99, slow VMs, stalls, time to ready, pass or fail, the knee and the recommended step marked), the settings in plain words, the test VMs with their OS, node, state, last IOPS and last p95, and the run log, newest first. Five live graphs over the whole run, read again every 30 seconds while it runs, with a mark at the start of each step: VMs running (Linux, Windows, not ready), IOPS (share, guests, IBM operations, against the share limit), latency (median and worst VM p95, and the share, against the latency limit), throughput, and the percent of slow VMs against the knee threshold. A New run form starts a run without a terminal: presets (quick check, one tier, three tiers one after another), every setting with help, the IOPS IBM allows for the share size, the load of each step in guest IOPS and IBM operations against the share limit, the run time, and checks before Run (the images, the memory of the largest step with one node down, the disks on the share); Run stays off until every check passes. The run page has the controls that fit the run at that moment (pause, resume, hold at this step, measure 15 minutes longer, skip to the next step, stop and clean up, clean up a run kept after its end), each with a note on what it does; stop, skip and clean up ask first. Downloads: the step table as CSV, a Markdown report, and a print view the browser saves as PDF; a run that has ended can be deleted. The raw results of every VM download as CSV, and each VM's own result lines open from the VM table; both come from the PoolBench service through the console's plugin proxy, only for people who may get the run. Tick two or more runs on the list to compare them: a graph of each run's p95 against the VM count, one line per run, and their steps side by side with the knee marked. Five events run on VMs that are already under load, once each, after a step is measured: a boot storm (every VM restarts at once), a patch window (every VM runs only bursts for 10 minutes), a live migration, a snapshot and a backup (10% of the VMs, at most 10; the backup goes to a second small share the run makes and removes). Ask for them in the new-run form or add one to a running run; the run page lists each with its time and what happened. See docs/specs/2026-10-25-poolbench.md.
    • Monitoring tab — Dedicated metrics page with time range selector (1h/6h/24h/7d), stat cards (allocation rate, P95 latency, VPC API health, replication status), and time-series charts (allocation rate, latency, API call rate by status, replication lag), and a collapsed section with the group snapshot inconsistency window, the group snapshot member count, and the times the controller raised CDI's copy limit.
    • Prometheus metrics panels — Stat cards and time-series charts using the driver's Prometheus metrics with usePrometheusRange hook for range queries.
    • TLS via service-ca — Plugin Service uses OpenShift's service-ca operator for automatic TLS certificate provisioning (no cert-manager dependency).

    CDI Copy Limit — Beta¶

    Lets VMs from the standard OpenShift Virtualization catalog use a pool for their boot disk.

    • Standard catalog — Pick a catalog image and choose the pool's StorageClass for the boot disk. CDI copies the image onto the pool. See USER-GUIDE.md.
    • Copy pod memory limit — The controller keeps the memory limit of CDI's copy pods at least 8Gi, through HyperConverged spec.resourceRequirements.storageWorkloads. It checks at start-up and every 5 minutes (leader only), and it only raises the limit. Helm value cdi.copyPodMemoryLimit; empty turns the check off.
    • Visible resets — Each raise logs a warning and adds 1 to vpc_file_pool_cdi_copy_limit_raised_total.
    • Measured — On rovslab, a 25 GB copy finished in 134 s with 8Gi and never finished with 2Gi. A RHEL 9 catalog VM had its guest agent after 103 s.
    • ROVS — IBM says the virtualization add-on cannot be modified. See KNOWN-LIMITATIONS.md.

    Golden Image Syncer — Hidden¶

    Hidden. The code is kept for possible later use. The console pool form no longer offers golden images, and the "VM storage" preset no longer turns them on. A pool that sets spec.goldenImages in YAML still works. The standard catalog is the recommended way to make VMs. The features below stay listed for that reason.

    VM image caching for KubeVirt workloads.

    • CDI DataImportCron discovery — Finds golden images defined by CDI DataImportCrons and syncs them to target namespaces.
    • CDI import — Makes a CDI DataVolume golden-<image> in each target namespace, on the pool's StorageClass, from the registry URL of the DataImportCron (pullMethod: node). CDI converts the image to raw. For ImageStream-based crons (RHEL), the syncer uses the external address the ImageStream imports from. The image is ready when the DataVolume phase is Succeeded. Target namespaces need no anyuid grant.
    • Configurable refresh interval — Default 24-hour sync cycle. Per-pool configuration via GoldenImageConfig in the FileSharePool spec.
    • CDI DataSource creation — Creates DataSource CRs in openshift-virtualization-os-images, named <image>-<namespace>-nfs-pool (one per golden claim), for InstanceTypes catalog visibility. Each points to the golden PVC in its target namespace. Creating a VM from the InstanceTypes tab with its boot disk on the pool is being tested.
    • Pool deletion clean-up — Deleting a pool deletes its golden DataVolumes, PVCs, Templates and DataSources first. The syncer skips pools being deleted. The syncer refuses a golden-<image> DataVolume that the pool did not make.
    • Per-namespace status — Tracks sync phase (Pending, Syncing, Ready, Failed) per target namespace.
