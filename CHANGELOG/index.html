    Changelog¶

    All notable changes to this project will be documented in this file.

    The format is based on Keep a Changelog.

    How versions work¶

    A version is a git tag vX.Y.Z. The driver reports git describe: v0.13.2-59-g2f04e1e means 59 commits after v0.13.2.

    To make a release:

    1. Move the items under Unreleased to a new heading ## [vX.Y.Z] — date.
    2. Add the section and the compatibility row to UPGRADE-GUIDE.md.
    3. Set version and appVersion in charts/ibm-vpc-file-pool-csi/Chart.yaml to X.Y.Z.
    4. Tag the merge commit vX.Y.Z and push the tag.

    v0.11.0, v0.13.0 and v0.13.1 were tagged on 21 October 2026, at the commit that added their changelog entry. v0.13.2 sits at e2b780f, the last commit of 25 February 2026: the commit that first added its entry (a2c2a07) lacked the TLS work the entry names. v0.10.0 and v0.12.0 were written in the same commits as v0.11.0 and v0.13.0, so they have no tag of their own. The chart said 0.1.0 until v0.14.0.

    [Unreleased]¶

    Added¶

    • VM disks in backups, part 4: gateway, kubectl backup --fs and the console picker (issue #92, phase 5). The gateway makes a guest session or a guest restore for every volume the policy status shows as a VM disk, and refuses a VM disk in COS in words. Session and Restore replies have guest. kubectl backup ls with no --fs lists the file systems of the disk (with the reason beside one that cannot be read); ls, get and restore-files take --fs (a name like sda1 or a device like /dev/rhel/root) and put it before the path; notices of the session go to standard error; a VM disk session gets 20 minutes to start. The console file browser asks for a file system at the top, marks a volume that cannot be read with its reason, shows crash-copy and journal warnings, hides the tar of the whole disk and explains the hold; the restore dialog explains that the file system name stays in the restored tree. A VM that was stopped when it was backed up (copied as plain files) is read from its moments folders, like any volume. New release test part 7 (test/e2e/test-backup-files-vm.sh, stage 20), not run yet.
    • VM disks in backups, part 3: restore of files from inside a VM disk (issue #92, phase 5). BackupFileRestore has spec.guest. The restore Job runs in the guest image with the new browse --mode=restore-files (the same restore code as the driver's, now in filerestore.Main), reads the file systems inside disk.img through the read-only appliance and writes to a new claim or a new folder of an existing claim; the first name of each path is the guest file system and is kept in the restored tree. The controller holds the disk (the same per-UID hold as a browse session) before the first Job, waits for a copy that is running, and releases the hold when the restore ends. The restore records when it first held the disk (status.guestHoldStarted) and fails after 2 hours 45 minutes, so a hold that was let go cannot be taken again; each Job runs for what is left of that time (2 hours at most). The pod has two containers: the reader parses the disk and has no write access to the target and no capability; the writer (browse --mode=restore-writer) holds only the target (the claim's folder, or the share for a new claim) and CHOWN and FOWNER, never sees the disk, and checks everything the reader sends. The counts and the restored folder in the status come from the writer's own termination message (read by container name), never from the reader's, which parses the untrusted disk; the reader gives only the moment and what was left out or unreadable, and a writer with no outcome fails the restore (#347). The webhook and the controller refuse a guest restore from COS, and the controller refuses a volume that is not a VM disk or an installation without the guest image, in words. Slow for many small files (an appliance start for each). The gateway, kubectl backup and the console come in the next change.
    • VM disks in backups, part 2: the guest helper and the file system reader (issue #92, phase 5). New package pkg/guestfs shows the file systems inside a backed-up VM disk as a read-only browse.Tree: the top level folders are the guest's file systems (from virt-filesystems), and below each one virt-ls and virt-cat list and read the files. Volumes that cannot be read (LUKS, BitLocker, ReFS, ZFS, RAID members, swap, unknown types) are listed with the reason in words. Parsers are strict and fuzzed; a device name from the disk is accepted only if it is plain (a colon would add mount options), names go to the tools as separate arguments after --, never to a shell or a script. A crash copy that does not mount is read again without its journal (norecovery, noload), with a notice. browse --guest serves it (the browse API now has entry.note and info.guest, info.consistency, info.notices); Dockerfile.browse-guest builds the image from CentOS Stream 9, pinned by digest, with libguestfs, libguestfs-winsupport and guestfs-tools. The controller starts the pod (new flags --browse-guest-image, --browse-guest-kvm, --browse-guest-cpu-limit, --browse-guest-memory-limit, --browse-guest-start-timeout; Helm values backupBrowse.guest.*, off by default until the image is built and pushed). The pod has the same rights as the plain helper plus two size-limited scratch folders and, if asked, the KVM device. Nothing creates a session on a VM disk yet: the gateway, kubectl backup and the console come in the next change. The image has not been built or run (the lab does that).
    • VM disks in backups, part 1: the disk view, the disk server and the hold (issue #92, phase 5). replication.OpenDiskView shows a backed-up VM disk as it was at any restore point, read-only, rebuilt on the fly from disk.img and the undo files (no copy, no scratch space); a property test checks every moment byte for byte against RestoreDisk over random histories, including growing and shrinking disks. The new package pkg/nbd serves a view to a client as a read-only network block device on a private socket, with the request and option parsers fuzzed. BackupBrowse has spec.guest: a session on a VM disk holds the disk's next backup copy (the SubVolume annotation storage.ibmcloud.io/browse-hold, one entry per session), waits for a copy that is already running, and the replication controller makes no new copy of a held volume (held: waiting for a browse session; all disks of a running VM are held together). A hold ends with its helper and is ignored after 3 hours. Nothing creates a guest session yet: the guest helper image and the commands come in the next changes. See BACKUP-RECOVERY.md.

    Fixed¶

    • Listing a folder inside a VM disk works. The first lab run showed that virt-ls 1.52 refuses -l --csv ('used a flag which can only be combined with -lR mode'). The reader now runs virt-ls -lR --csv and keeps the names directly in the folder. Regular files, which virt-ls marks with -, were shown as 'other'. A folder with a very deep tree is slow to list, because -R reads the whole tree.
    • Holds on a SubVolume can no longer be wiped by another writer, and a copy that runs is waited for. Removing the last annotation with a patch made from a copy said annotations: null and wiped the other holds, so releasing an export hold or sweeping a browse hold could drop a hold that another writer had added a moment before. Hold writes now name only their own key, and the browse hold list is written only if the SubVolume is as it was read. A volume with a copy Job is not held until the Job has ended and been cleaned up: before, its status said "held" at once, the Job was never looked at again, and a browse session could start while the copy still wrote.

    [v0.16.3] — 2026-10-30¶

    A fix release: a new pool can no longer end with a share that has no mount target (found by beta run 2). Built from v0.16.2 plus this fix only; the Unreleased items below are not in it.

    Fixed¶

    • A new pool no longer ends with a share that has no mount target (issue #366). The pool status is now saved again after a resourceVersion conflict (also when provisioning stops half way), so shares already created in VPC are recorded and the next pass does not create them again. A recorded share with no mount target now switches to the share of the same name that holds the mount target and its network interface, and the bare duplicate is deleted when no volume lives on it. Adopting a share by name prefers the one that has a mount target. Cause: when a share create call failed while building its inline mount target ("Provided Name ... -mt-vni is not unique", HTTP 500), VPC could keep a bare share of that name next to the complete one, and the next pass adopted the bare one.

    [v0.16.2] — 2026-10-29¶

    A fix release: a wrong COS key is named as the cause when browsing or restoring from COS.

    Fixed¶

    • A wrong COS key is now named as the cause when browsing or restoring from COS. COS often answers a wrong key with only a message ("The AWS Access Key ID you provided does not exist in our records", or a signature mismatch) and no error code, so the user was told only that COS could not be read. Found in release test stage 20.

    [v0.16.1] — 2026-10-29¶

    A fix release. Audit Events for backup browsing and file restore are now recorded, the gateway address is filled in on a first install, and the console shows a policy's last error as an error.

    Fixed¶

    • Audit Events for backup browsing and file restore were refused by the API server. The gateway and the controller wrote them on the BackupBrowse or BackupFileRestore, which have no namespace, and the API server accepts an Event for such an object only in default, where many people can read. The gateway logged the Event and then failed to store it. The Events are now on the ConfigMap backup-gateway-info in the driver namespace and name the session or restore in related. Found in the first lab run of release test stage 20.
    • The policy's last error is shown as an error in the console (issue #46). On the replication policy page, the Last Error line is now a red inline alert with an icon instead of plain text, and shows - when there is no error.
    • The gateway address is filled in on a first install. The ConfigMap backup-gateway-info had an empty address after the first install on OpenShift, because the Route did not exist yet, so kubectl backup needed --gateway until a second helm upgrade. The chart now uses the host the router will give the Route.

    [v0.16.0] — 2026-10-28¶

    A feature release. Failover from the console: a new Failover resource plans and runs a failover on the destination cluster, for all VMs or for chosen VMs, and the console has a Recovery page for it. Files from a backup: browse, download and restore single files and folders from the backups of plain volumes, in the snapshot pool or in COS, from the command line and the console, through a new backup gateway. Two new CRDs (Failover, BackupFileRestore), new chart objects (the gateway, a browse namespace) and a new role. VM disks inside backups are not covered yet.

    Added¶

    • Release test stage 21: failover of chosen VMs, and a browser test of the Recovery page (issues #44 step 4 and #46). New stage test/release/stages/21-failover.sh (needs a second cluster: RT_DR_CLUSTER=NAME bash test/release/remote.sh start CLUSTER TAG). It replicates two running VMs and a plain volume to a receiver on the DR cluster and checks that a Plan with vms shows only the chosen VM; an Execute with a different list is refused and makes nothing; an Execute for one VM with rewindTo makes only that VM's PVCs, PVs and SubVolumes and rewinds only its two disks; the VM boots on DR from the chosen moment (no XFS errors, every logged file with its checksum, no file after the moment); a second Execute is refused as already failed over; and the second VM fails over in the Recovery page. The new Playwright test console-plugin/integration-tests/tests/recovery.spec.ts covers the VM table, the detail view, the typed VM name, the cancelled dialog and the progress to Done. The browser tests for drain, migration and clone (#46 items 5, 6 and 7) already exist (drain.spec.ts, migrate.spec.ts, clone.spec.ts, run by stage 16). Not run on a cluster yet. See TESTING.md.
    • Browse and restore files from a backup in COS, plain volumes (issue #92, phase 4). BackupBrowse and BackupFileRestore have spec.source (local or cos) and spec.fromCOS (a bucket named directly, for a cluster administrator). kubectl backup ls, get, browse and restore-files take --from-cos, with --bucket, --endpoint and --volume (and the key flags of restore --from-cos) to name a bucket. The gateway reads COS by itself when a moment is older than the oldest local restore point, or no local copy is left and an export exists, and source: cos asks for it; the gateway's volume list shows exported and exportedTime. The browse helper (cmd/browse, new flag --cos-source) and the file restore Job read the Kopia repository through the pinned Kopia program as a child process (now also in the browse image), read-only: folders are read as JSON and walked by object IDs, so a user's path is never an argument and a link leads nowhere; snapshots are chosen by tag and by the exact source path of the volume, so no other volume or policy in the bucket area is read. The backup key is unwrapped in the helper's memory; the Kopia child gets an explicit environment. The COS helper runs in the driver namespace, next to the COS and Key Protect Secrets, with no service account token and as an ordinary user, and the controller keeps a copy of the session Secret there; the keys are never copied to the browse namespace where the gateway may read Secrets. Naming a bucket directly needs the right to read each Secret it names in the driver namespace (checked by name, on every call). A wrong root key, a missing Secret, a wrong COS key and a missing repository are said in words in the session status; a session whose helper is not ready after five minutes ends with a message that names the Secrets to check. New Helm values backupBrowse.cos.*, a Role (create and delete Secrets) and a NetworkPolicy in the driver namespace. Stage 20 part 6 of the release test checks it on the lab (not run yet; it needs a COS bucket). Not yet: VM disks in COS (phases 5 and 6), and a source switch in the console file browser. See BACKUP-RECOVERY.md.
    • Restore chosen files from the console (issue #92, phase 3 second half). The file browser has a checkbox on each file, folder and link, a line with the number chosen and the total size of the files, Restore selected and Clear. The restore dialog restores into a new claim (default; optional size and storage class) or a new folder in an existing claim (turned off, with the missing rights named, for a user without them, using access reviews on the target namespace), shows what will be written, the moment, and a warning that nothing is overwritten, then follows the restore by polling every 2 seconds through its phases and shows links to the claim and folder, the counts and the size. A refusal is explained in plain words (403 names the missing right, 404, 409 suggests another name, 429 too many open restores). A file inside a chosen folder is not sent twice. Console only; no change to the gateway, the chart or the CRDs. Help link and guide section: BACKUP-RECOVERY.md.
    • Restore files from a backup into a claim, part 5: gateway and kubectl backup restore-files (issue #92, phase 2). Users can now ask for a file restore. kubectl backup restore-files --policy P --pvc NS/NAME --path A --path B --to NS/CLAIM [--existing | --new-claim --size-gb N] [--moment T] [--wait] (also --paths-file and --status NAME) calls the new gateway endpoints POST /v1/restores and GET /v1/restores/{name}. The gateway checks the user's own token and, as the user, get backupfiles in the namespace of the backed-up claim, create on persistentvolumeclaims in the target namespace and, for an existing claim, update on claims and create on pods (writing into a claim is the same power as mounting it). The access check is now a general "may this user do this in this namespace" (Authorizer.Can). The gateway reads the existing claim only after the rights are known and pins its UID in the restore, so a claim that is deleted and made again is refused. A restore is shown only to the user who asked for it. A user may have 10 restores that have not ended (backupGateway.maxOpenRestores). Each request writes an audit Event FileRestoreRequested with the user, the volume, the moment, the target and the paths. The gateway's cluster role gets get, list, create, delete on backupfilerestores and get on persistentvolumeclaims. Stage 20 part 5 of the release test checks the user path on the lab with real users.
    • Restore files from a backup into a claim, part 4: BackupFileRestore (issue #92, phase 2, resource and Job). A new cluster-scoped resource copies the files and folders you list out of one backup into a new claim (sized to the files plus 20%, at least 1 GiB, by a read-only Job that runs first) or into a new folder of an existing claim (restored-<policy>-<moment>). It never writes over a file that exists and never writes into a VM disk. A symbolic link is copied as a link and never followed, on the backup side or in the claim; setuid and setgid are removed; times and modes are kept; the owner is the one the claim is configured with. The Job is the driver program (--mode=restore-files), not a shell: the paths are a file in a ConfigMap that the restore owns. It writes a hidden staging folder in an existing claim and renames it at the end, checks the space first (the least of 200 GiB, the share's free space and the claim's size less what it holds), refuses a claim that holds disk.img, a claim with no data folder yet, a claim being restored, and a claim that was deleted and made again since the request, and removes what it wrote if anything fails (a file whose owner cannot be set fails the restore). One restore at a time writes into one claim. The validating webhook, the controller part, the chart and config/rbac roles, the backupBrowse.restoreMaxBytes and backupBrowse.restoreMaxRunning (at most 5 restores at once; more wait) values and docs are in. Users cannot ask for it yet: only a cluster administrator can make the resource; the gateway call and kubectl backup restore-files come in the next part. The file restore Job reads the backup with the browse helper's handle-based reader (now browse.ChooseRoot, moved out of the helper's main). Also: a share Job that fails now keeps the reason its container wrote.
    • Browse and download files from a backup in the console (issue #92, phase 3 first half). The Browse files action on each volume of a backup policy opens a file browser with folders in pages, breadcrumbs, a moment picker, symbolic links shown as links and never followed, names shown as escaped text, "not readable" entries, session states (starting, ready, ended) with polling and no long request, and a session close when you leave. A file downloads as a file and a folder as a tar, through the console plugin proxy with the person's own token. The gateway has a new GET /v1/sessions/{name}/download route (same session, rights, size limit and audit Event as the POST calls) and now sets Content-Disposition: attachment, X-Content-Type-Options: nosniff, Content-Security-Policy: sandbox; default-src 'none', Cache-Control: no-store and a fixed content type on every file and tar reply, because the console serves the reply from its own origin. The chart adds a backup-gateway entry to the ConsolePlugin proxy (only when the gateway runs; the PoolBench entry is kept) and a fileBrowse key to the settings ConfigMap that tells the console whether to show the action. The file restore dialog is not part of this change. See BACKUP-RECOVERY.md.

    • Chart tests for the gateway and the browse namespace now run in make test-scripts. test/chart/test-gateway.sh and test-browse.sh were not listed there. test-browse.sh had a failing check (off: no Role) that matched the settings Role; it now checks that nothing is made in the browse namespace.

    • A failover can be limited to one VM or a chosen set (#328). Failover has a new optional list spec.vms (namespace/name). Empty is today's behaviour: every VM on the copy and every volume that is not a VM disk. With a list, only the chosen VMs are read, planned and failed over, all disks of a VM together; plain volumes are left out. A name that is not a running VM on the copy fails the Plan and says which VMs the copy holds. An Execute needs a finished Plan with the same source, rewindTo and vms (compared as sets). The Job (new flag --vms), the "already failed over" checks, the status and the created SubVolumes, PVs and PVCs cover only the chosen VMs, and a copy still being applied to another VM no longer blocks them. kubectl failover plan and execute take --vms ns/name,.... In the console Recovery page, "Fail over this VM" in the VM detail plans and fails over that VM only, and the confirm dialog asks for the VM name again; an explicit "Fail over all VMs" button keeps the old behaviour. Experimental.

    • The console has a Recovery page to fail over a VM from the copy (#44, step 3). Under Replication, a new Recovery page (link on the Replication tab) makes a Failover with action: Plan and shows the running VMs found on the copy: disks, disks to rewind, the moment each will show and how many moments can be chosen. Refresh makes a new plan. The copy to read is filled in when the cluster has one replication receiver, and chosen by the operator when it has several. A VM opens to its disks (a disk that must be rewound says it copies the whole disk and takes minutes) and its moments, newest first. Fail over opens a dialog that lists the VMs, the moment, the disks to rewind and the PVCs that will be made, asks for the DR pool, and needs a typed confirmation. It then makes an Execute with the source and rewindTo of the confirmed plan; a moment other than the one on screen first makes a new plan with that rewindTo. A failover covers everything on the copy, so with more than one VM the dialog says so and the operator types the source name. While a copy is applied to a disk the Job refuses; the page shows the refusal and offers force only behind a second warning. The page shows the phase, a still-working state with the time it has run, the created PVCs with links, and the message of a failed Failover. A warning shows when the newest copy is older than twice the schedule of the policy that wrote it (when that policy is on this cluster). The page uses the rights of the signed-in user and the chart adds no role: without the right to create a Failover it says that the failover-admin role is needed. Experimental.

    • The replication policy page shows how each running VM can be recovered (#44, step 2). The policy status has a new list vms: for each running VM, its disks, the copy moment, the consistency and commonMoments, the moments that all its disks can show (the copy moment and the restore points every disk has), newest first. Only those moments are safe, because disks rewound to different moments would give the guest a mix of two times. The name of the replication policy a backup policy makes (backup-<policy>-<pool>-<hash>) is a label value on the temporary volume of a copy, and it went over 63 characters for a policy and pool name of about 25 characters each. The copy failed on every cycle with "must be no more than 63 characters", and the VM disks, which use another path, still worked. The name is now cut to fit; names that already fit stay as they were. Found by release stage 18 on the lab.
    • A VM disk made by a CDI clone (for example a VM from the OpenShift console catalog) is now seen as the VM's disk. CDI provisions the clone through a temporary claim and then binds the volume to the VM's claim; the SubVolume kept the temporary claim. The driver then did not find the running VM, so a snapshot of a running VM's disk was a plain file copy, not an instant or QEMU snapshot. A new controller sets the SubVolume's claim to the claim its volume is bound to, also for volumes that exist already.
    • A slow snapshot, snapshot delete or restore no longer makes every other volume's create and delete wait. Each of these calls now locks only the volume it changes; the driver-wide lock is held just for the share's space bookkeeping. Two changes to the same disk still never run at once (issue #99).
    • Deleting a pool no longer deletes the data of its snapshots. The pool waits while snapshots exist (DeletionBlocked reason SnapshotsExist), and a drained share counts its snapshots too (new status.drainStatus[].remainingSnapshots). A snapshot whose pool an older driver already deleted can now be deleted; before, its delete was stuck for ever (issue #96).
    • A snapshot's space charge on its share now survives the pool's regular recount; before, the next reconcile dropped it, and the later delete then counted the share too low. A snapshot no longer counts as a PVC, and a share that has no room for a snapshot refuses it with ResourceExhausted instead of being over-committed (issue #97).
    • A restore into a volume smaller than the snapshot is refused (OutOfRange) instead of making a volume the data does not fit in (issue #98).
    • Replication finds a VM disk whose top file is not disk.img.

    Changed¶

    • VMs now come from the standard OpenShift Virtualization catalog. Pick a catalog image and choose the pool's StorageClass for the boot disk. CDI copies the image onto the pool. The controller keeps the memory limit of CDI's copy pods at least 8Gi, through HyperConverged spec.resourceRequirements.storageWorkloads. CDI's default of 600 MB is too small for copies onto NFS: the pod is killed. Measured on rovslab on 20 October 2026: a 25 GB copy with a 2Gi limit was killed 6 times and never finished. With 8Gi it finished in 134 s and the checksum matched. A RHEL 9 catalog VM on a pool had its guest agent after 103 s.
    • Golden images are hidden from the console pool form. The pool form no longer offers them, and the "VM storage" preset no longer turns them on. The code is kept for possible later use, and spec.goldenImages still works if a pool sets it in YAML. The standard catalog is the recommended way.
    • The release test makes its VMs from the standard catalog (stage 08), copies 25 GB from Ceph with CDI and checks the checksum, and checks CDI's copy pod limit in stage 01.
    • Release test stage 16 restores a snapshot to a new claim in a real browser (issue #45, part 2). A second console runs with a write token that works in the test namespace only; the read-only token for the first browser run is unchanged. The stage then reads the new claim from a pod and checks the files against the data at snapshot time.
    • CDI clones onto a pool are made by the driver. The pool's CDI StorageProfile now sets cloneStrategy: csi-clone instead of copy. CDI's host-assisted copy pods (memory limit 600 MB) were killed for lack of memory when they wrote onto NFS: 3 of 3 copies on rovslab, onto a pool and onto IBM VPC File alike. Copying a catalog image from other storage, such as Ceph, onto a pool still uses those pods. They now have a higher memory limit (see below).
    • Golden images are imported by CDI. The syncer now makes a CDI DataVolume golden-<image> in each target namespace, on the pool's StorageClass, with the DataImportCron's registry URL as source (pullMethod: node). For ImageStream-based crons (RHEL), it uses the external address the ImageStream imports from. A golden image is ready when the DataVolume phase is Succeeded. On rovslab, CentOS Stream 9 imported in about 40 s and RHEL 9 in about 2.5 min, and VMs booted from both. Catalog entries (DataSources) are now named <image>-<namespace>-nfs-pool, one per golden claim. Two pools must not send golden images to the same namespace.
    • Shares use security group access mode. IBM has deprecated VPC access mode (End of Support 6 May 2027), and the VPC API now refuses new VPC-mode mount targets with HTTP 501, so the driver could not create usable storage on a new cluster. Each share now gets one mount target with a virtual network interface in the worker subnet of the pool's zone, protected by the cluster security group kube-<cluster ID>.
    • The controller reads every subnet in vpc_subnet_ids (and --subnet-id accepts a comma-separated list) and picks the one in each pool's zone. It used to take the first subnet, whatever its zone.
    • A pool is Ready only when at least one share is stable and has a mount target address. Otherwise it is Degraded, and the SharesReady condition (reason NoMountTarget) names the shares. Pools do not add shares while a share is still being created or has no mount target.
    • accessorZones[].subnetID is now optional and not used: one mount target in the home zone serves every zone.
    • metrics.serviceMonitor.enabled is now true by default. The chart creates the ServiceMonitor only when the cluster has the Prometheus Operator API, so installs on other clusters still work.

    Security¶

    • The replication receiver no longer runs with the controller's rights (#89). It had the controller's ServiceAccount, which reads Secrets and execs into pods in every namespace, although it takes data from outside the cluster and never calls the Kubernetes API. It now has its own ServiceAccount with no role and no API token, and the pod cannot gain privilege. The bearer token is compared in constant time, an empty token is refused, and the receiver will not start with a token shorter than 32 characters (openssl rand -hex 32 makes 64). Upgrade note: a shorter token must be replaced on both clusters. The receiver also writes only into pvc-<uuid> folders now, so a token holder cannot write elsewhere under the base path. Not done yet: TLS on by default.
    • Go libraries updated for 13 known advisories (#90). google.golang.org/grpc 1.79.1 to 1.83.1 (up to CVSS 9.1), golang.org/x/net 0.48.0 to 0.60.0 (six advisories), golang.org/x/text 0.32.0 to 0.42.0 and github.com/moby/spdystream 0.5.0 to 0.5.1. The newest x/net and x/text need Go 1.26, so the project, the build image and CI now use Go 1.26. Whether each advisory could be reached by the driver was not checked.
    • A ReplicationPolicy could run commands as root in kube-system (#88). spec.rsyncOptions and spec.destinationBasePath were put into the copy Job's shell script without quotes. The webhook now accepts only plain rsync flags (such as --compress or --bwlimit=100) and an absolute base path of letters, digits, ., _, - and /, and the controller quotes every value in the script, so a policy made with the webhook off is safe too. A policy that used a space, quote or ; in rsyncOptions is now refused.
    • A user in a target namespace could pre-create the golden-<image> DataVolume and have it published to the shared catalog. The syncer now refuses a DataVolume that the pool did not make (missing pool labels, or a different source URL or StorageClass) and publishes no catalog entry for it.
    • Pool deletion trusted labels in any namespace. It now removes only objects in the pool's own target namespaces.
    • Replication receiver: a tar upload could write files outside the destination volume through a symlink (a sibling directory whose name starts with the destination's name, or a symlinked parent directory). All writes now go through os.Root, and symlink targets are checked against the parent's real location.

    Fixed¶

    • The console's "High-IOPS Database" preset asked for 48,000 IOPS on 4,000 GB shares. IBM allows 40,000 at that size, so a pool made from the preset would not get its shares. The preset now uses 40,000.
    • kubectl-migrate ignored the KUBECONFIG variable. It read only ~/.kube/config, so it failed on any machine that sets KUBECONFIG. It now uses --kubeconfig, then KUBECONFIG, then ~/.kube/config, and says so when none exists.
    • kubectl-migrate reported success when files were missing. If the file counts of the old and new claim differed, the copy pod only printed a warning and exited with success. The pod now fails, and so does the tool.
    • A drained share never came back into use. Once a share was marked draining, by a drain request or because the VPC reported it degraded, it stayed draining after the request was removed or the VPC reported it healthy again. It got no new volumes but was still billed. A healthy share that is not on the drain list is now back in use.
    • Replication failures could go uncounted, so a failing policy never paused. A cycle was judged only when all its copy Jobs had finished at once, but a volume whose Job finished early got a new Job on the next check. With Jobs that finish at different times, that moment might never come. A volume's result is now kept until every volume of the cycle has finished.
    • While a new copy ran, or after one failed, the policy status dropped each volume's last good sync time. It now keeps it, so the age of the last good copy stays visible.
    • The replication controller read pods through the shared cache, which needs a watch permission the controller does not have, so the running-VM check could fail. It now reads directly.
    • The FileSharePool webhook allowed expandThresholdPercent 1–99 and maxShares up to 1000, but the CRD schema allows 50–95 and up to 100. The webhook now uses the schema's ranges, so its messages give the real limits.
    • VMs made from a golden image template could not get a boot disk. The template always asked for a 15 GB boot disk, but a copy cannot be smaller than its source, and CDI makes a disk a little larger than requested. The golden disk is now exactly the pool's pvcSizeGB, and the template's boot disk defaults to the same size.
    • A pool with golden images could not be deleted. The syncer made the golden disks again while the pool was being deleted. Deleting a pool now deletes its golden DataVolumes, claims and Templates in its target namespaces, and its DataSources, before the pool. The syncer skips pools that are being deleted.
    • The catalog showed stale or missing golden images. Catalog entries stayed after their pool was deleted, and every entry for an image had the same name, so only the first namespace of the first pool got one. Entries are now named per namespace and removed with the pool.
    • Golden images needed anyuid in the target namespace. The converter ran as root in the app's namespace. CDI now does the import, so no extra permission is needed.
    • Replication copied the disks of running VMs, and the copies might not boot. The copy read the disk while the VM wrote to it, so it mixed data from different moments. The controller now skips any volume that a running or starting VM uses, and the volume's status names the VM pod. Skipped volumes do not pause the policy. A copy during which a VM started is not recorded as a sync. Volumes of stopped VMs replicate as before.
    • Clones needed root permission in the app's namespace. The clone copy Job ran in the claim's namespace as root, so a clone failed unless that namespace had the anyuid permission. Clone copies now run as share data Jobs in the driver's namespace, mount the shares directly, and leave nothing in the app's namespace. Deleting a clone while it copies stops the copy first.
    • Deleting a volume left its data on the share, and snapshots held no data. The controller has no NFS access, so it skipped every data step and still reported success: a deleted volume's folder stayed (the pool showed the space as free), a snapshot was marked ready with nothing copied, a restore gave an empty volume, and a deleted snapshot removed nothing. Kubernetes Jobs in the driver's namespace now do these steps. A volume's space is given back only after its folder is removed, a snapshot is ready only after its copy, and a restored claim binds only after its copy.
    • A retried CreateVolume for a clone or restore answered from the existing record, without naming the source. The provisioner rejected that answer and tried to delete the new volume. Retries for clones and restores now go to the pool manager, which checks the copy and names the source.
    • A retried CreateVolume for a volume that already exists returned the share path / and no owner or permissions. If the provisioner built the PV from that answer, the volume could not mount, and a KubeVirt volume would get the wrong owner. The answer now matches the first one.
    • The console plugin's pool create page offered a custom profile, which VPC file shares do not have, so such a pool never got a share. It also said dp2 gives 100 IOPS per GB; the VPC gives 100 IOPS per share unless you set the IOPS. The page now offers only dp2, and the IOPS field works with it (0 lets the VPC choose). The Standard and KubeVirt presets now set 1,000 and 3,000 IOPS; the High-IOPS preset uses dp2.
    • The Pools page said the pool manager balances shares across availability zones. A pool is in one zone, and volumes are never moved between shares. The text now says what the pool manager does.
    • The pool controller reconciled each pool every 1 to 2 seconds instead of every 60 seconds, because its own status write started the next pass. Each pass calls the VPC API. On rovslab, one pool made about 30 VPC calls a minute.
    • The console plugin showed IOPS as 100 per GB when a pool sets no IOPS. The VPC chooses the IOPS in that case (a 100 GB dp2 share got 100, not 10,000), so the plugin now shows "VPC default".
    • The console plugin's pages are now in the Storage menu of the Virtualization perspective too.
    • Replication policies paused after maxRetries were resumed on the next cycle and kept creating Jobs. The automatic pause now sets the storage.ibmcloud.io/paused annotation; removing it resumes the policy and resets the failure count.
    • CreateVolume returned success for a volume whose clone had failed. It now returns an error with the clone failure.
    • Sync client: a CA bundle with no usable certificate was ignored silently; NewSyncClientWithCA now returns an error. The client requires TLS 1.2 or later.
    • Concurrent uploads to the same destination are serialized.
    • Security group mount targets were recorded with the export path / instead of the share's own export, so every NFS mount would have failed.
    • Shares created by auto-expansion had no mount target, because that path passed no network details. All share creation now goes through one function.
    • Adopting an existing share after a retry did not record its export path.
    • Restoring a volume from a snapshot while the pool was growing failed with Internal; it now returns a retriable Unavailable, the same as a new volume or a clone.
    • .golangci.yml used v1 keys under version: "2", so its settings were ignored. All lint findings are fixed, and the integration tests compile and pass again.
